## D01 职责边界

**背景**　"把电脑用作可供公网访问的服务器"存在三种截然不同的产品形态。

**结论**　ISC 是**接入编排器**：只负责"让外部能访问到本机"。业务服务（Jellyfin / Minecraft / nginx / SSH）由用户自行安装，ISC 不托管其生命周期。

**理由**　托管业务服务（应用市场 + 服务管理器）的跨平台差异极大，工作量翻 2~3 倍，且会把项目拖入与 1Panel / 宝塔的同质竞争，而 ISC 真正的差异化在"无公网 IPv4 的家宽如何被公网访问"。

**后果**
- 内核不提供"一键安装应用"能力；GUI 阶段也不做。
- 内核必须把"可达性"做到极致（这是它存在的全部理由）。
- 端口/防火墙/证书/反代属于内核职责；进程守护业务服务不属于。

## D02 可达性策略

**背景**　国内家宽普遍无独立公网 IPv4，仅有动态 IPv6。需求是"仅用动态 IPv6 + 动态域名解析"实现公网访问。同时存在多个现实约束：

- 家宽重拨后 IPv6 **前缀（/64）会变**，不是单个地址变；
- 国内家宽普遍**封禁入站 80/443**（部分省份连 8080 也封）；
- 家用路由器 **IPv6 防火墙默认丢弃入站**，而 UPnP-IGD 只管 IPv4，对 IPv6 无效；
- 访问端若只有 IPv4（公司网、部分公共 WiFi），纯 IPv6 走不通。

**结论**　MVP 只实现 **IPv6 原生**一种可达方式，但从第一天起把"可达方式"抽象为 `ReachabilityProvider` 接口。frp / Cloudflare Tunnel / 端口映射等都是后续插件，内核不改。

**理由**　先把唯一能确定走通的路径做扎实，避免在隧道与打洞上过早发散。

**后果**
- `internal/reach/` 必须从 M0/M3 就存在接口定义，即使只有 `ipv6-native` 一个实现。
- `isc doctor` 必须能区分"本机没通"与"运营商封了端口"。
- IPv6 前缀跟踪是一等公民，不是 AAAA 记录的附属功能。

## D03 进程形态

**背景**　内核与 GUI 的解耦质量、"应用响应速度"、以及服务可靠性三者在此交汇。

**结论**　**独立守护进程 + 本地 API**。`isc-core` 是独立二进制，可安装为系统服务常驻；GUI 是纯客户端，通过命名管道 / Unix socket / 回环 HTTP + Bearer token 连接。

**理由**
- GUI 崩溃或关闭不影响 DDNS 定时任务 —— 服务器场景的硬要求；
- 核心常驻才能保证可靠性（开机自启、崩溃重启）；
- 以系统服务身份运行才能静默绑定低端口、修改防火墙；
- GUI 技术栈可随时更换，且不继承 GPL（见 D17）。

**后果**
- 需要服务安装流程与提权时机设计（安装时一次性提权）。
- 需要"GUI 如何发现内核"的机制：`runtime.json`（pid / 传输地址 / 随机 token）。
- 禁止把内核作为 Go 库链接进任何 GUI（架构红线，见 D17）。

## D04 DNS 能力分层

**背景**　ddns-go 的 34 个 provider 文件**只实现了"把 A/AAAA 记录新增或更新到当前 IP"**，查询/新增/修改逻辑写死在 A/AAAA 上；没有通用记录 CRUD、没有删除、没有 CNAME/MX/TXT/SRV/CAA、没有区域列表。`proxied`、`comment` 等 Cloudflare 特性是通过自定义查询参数 hack 进去的。

**结论**　**分层能力**：
- **Tier-1**：完整记录 CRUD（列区域、列记录、建/改/删、A/AAAA/CNAME/MX/TXT/NS/SRV/CAA、TTL、Cloudflare 代理开关）；
- **Tier-2**：直接照搬 ddns-go，只做 A/AAAA 动态更新。

用 Capability 接口声明能力位，GUI 据此自动置灰不支持的功能。

**理由**　30 家 × 全量 CRUD 的工作量是分层方案的 4~6 倍，且每家 API 的签名、错误码、分页差异极大，维护成本高。国内用户的真实需求高度集中在少数几家。

**后果**
- `internal/dns/providers/tier1/` 与 `tier2/` 分开组织。
- Provider 接口需支持能力协商（`Capabilities() CapabilitySet`）。
- 文档需明确列出每家的能力矩阵。

## D05 Tier-1 厂商名单

**结论**　Cloudflare、阿里云 DNS、腾讯云 / DNSPod、华为云 DNS、GoDaddy。

**理由**　覆盖国内自建服务器用户绝大多数；五家 API 风格差异足够大（Bearer Token / 阿里云 RPC 签名 / 腾讯云 TC3 签名 / 华为云签名 / GoDaddy 简易 REST），能一次性验证抽象层的通用性。前四家同时满足 ACME DNS-01 证书签发需要。

**后果**
- 这五家必须实现 `dns.Provider` 的完整能力集。
- ddns-go 中已有的签名代码（`util/aliyun_signer.go`、`huawei_signer.go`、`tencent_cloud_signer.go`）应直接复用而非重写。
- 其余厂商能力矩阵在文档中标注"仅动态解析"。

## D06 存储与凭据

**背景**　ISC 会把**能重写整个 DNS 区域的凭据**存在本机，而它自己又是个对公网暴露的服务器。凭据被盗 ≈ 域名被劫持。

**结论**　**嵌入式 SQLite（`modernc.org/sqlite`，纯 Go 无 cgo）+ OS 钥匙串加密凭据 + YAML 导入导出**。

- 主密钥存 OS 钥匙串：Windows DPAPI / macOS Keychain / Linux Secret Service；
- 无钥匙串时回退到 0600 权限文件，并明确告警；
- 支持 YAML 导入导出，用于备份、迁移与 ddns-go 配置导入。

**理由**
- 应用要管理大量实体（凭据/区域/记录/任务/服务/证书/规则/计划/任务/事件/审计），关系型查询与分页是刚需；
- 纯 Go SQLite 保证交叉编译不受 cgo 影响（关键：本机无 MSVC 工具链）；
- 明文凭据与"把电脑暴露到公网"的安全诉求直接冲突。

**后果**
- 需要密钥版本号字段以支持轮换（`key_version`）。
- 导出 YAML 时必须明确提示是否包含明文凭据（默认不含）。
- 需要 schema 迁移框架。

## D07 API 契约形式

**结论**　**OpenAPI 3.1 契约优先**。`api/openapi.yaml` 是唯一真理；`oapi-codegen` 生成 Go server 接口与模型；`openapi-typescript` 生成前端类型与客户端。

**理由**　接口数量轻松过百（5 家 Tier-1 CRUD + 可达性插件 + 防火墙 + 证书 + 任务 + 事件流）。手写 TS 类型到第 30 个接口就会开始漂移，而 GUI 是后做的，漂移代价全部由 GUI 承担。契约优先还能让编译期发现"实现漏了哪个接口"。

**后果**
- 改接口必须先改 spec。
- CI 必须包含"生成物漂移检查"（重新生成后 git diff 必须为空）。
- 自带 Scalar / Swagger UI 便于调试。

## D08 调用与推送模型

**背景**　DNS-01 证书签发要等 TXT 记录传播 + CA 轮询，典型 30 秒到 3 分钟；IPv6 前缀检测、provider 凭据校验、防火墙应用也都是秒级到分钟级。做成同步 REST 会导致 GUI 超时或假死。

**结论**　**快查询同步 + 慢操作异步 job + WebSocket 事件流**。

- 快查询（列表 / 详情 / 配置）保持同步 `GET`；
- 所有可能慢的操作返回 `202 Accepted` + `jobId`，进度通过任务接口或事件流获取；
- 内置事件总线，一条 WebSocket 推送 `job.progress` / `job.finished` / `ip.changed` / `cert.renewed` / `reachability.changed` / `log.appended` / `config.changed`；
- 事件带单调递增序号 + 环形缓冲，断线重连可按 `lastEventId` 补发；
- 多客户端（CLI + 控制台 + GUI）同时连接互不干扰。

**理由**　这是"响应速度"与"能力完整"唯一能同时满足的模型。

**后果**
- 任务状态必须持久化（进程重启后任务可查询/可恢复）。
- 事件序号需要持久化水位，否则重启后补发语义不清。
- 需要任务取消与超时语义。

## D09 管理接口安全边界

**背景**　ISC 内核掌握能重写整个 DNS 区域的凭据，还能改防火墙、绑低端口；同时它装在一台准备对公网开放的机器上。它的本地管理接口是一条"只要拿到就能接管你域名"的通道。ddns-go 的"Web UI + 账号密码 + 禁止公网访问开关"在本项目威胁模型下不足。

**结论**　**仅本机 + 强制 token**。

- 默认只监听回环；优先走命名管道（Windows，用 SDDL 限定仅当前用户 + 管理员）/ Unix socket（0600）；
- 首次启动生成随机 token 写入 `runtime.json`（仅当前用户可读）；
- 所有请求强制带 token，即使是回环；
- 内核管理面绝不对外暴露；
- v1 明确不做远程管理，但认证中间件留接口（未来可插 mTLS / OIDC）。

**后果**
- `runtime.json` 所在目录的 ACL 必须收紧。
- 控制台与 CLI 共用同一 token 发现逻辑。
- 若未来要做远程管理，必须新开一条独立监听 + 独立认证链，不得复用本地管道。

**实现现状（M0）**

- Windows：命名管道安全描述符 `D:P(A;;GA;;;SY)(A;;GA;;;BA)(A;;GA;;;IU)`——
  受保护 DACL，不含 `Everyone` / `Anonymous` / `Network logon`，
  因此 `\\host\pipe\isc-core` 形式的远程连接会被拒绝（网络登录的令牌不含
  INTERACTIVE SID）。
- `run/` 目录同样使用**受保护的** DACL（切断从 `C:\ProgramData` 的继承，
  否则 `Users` 的宽泛权限会继续生效），授权范围收敛到三个明确 SID：
  `SYSTEM` / `BUILTIN\Administrators` / `INTERACTIVE`。
- 令牌比较使用 `crypto/subtle` 常数时间算法；空令牌视为配置错误，
  拒绝所有请求而不是放行。
- WebSocket 场景下浏览器无法设置自定义请求头，因此额外支持用
  `Sec-WebSocket-Protocol: isc.token.<token>` 承载令牌，避免把令牌放进
  查询串（那会让它落进访问日志与历史记录）。

**⚠️ 已知局限（必须有意识地接受，而不是忽略）**

`runtime.json` 含访问令牌，因此**"可读"等价于"可控制内核"**。
在多用户共享的机器上，任何交互登录的用户都能读到令牌，进而控制一个以
SYSTEM 运行、能够修改防火墙的服务 —— 这是一条本地提权路径。

目标场景是家用单用户机器，此时 `INTERACTIVE` 就是机主本人，不构成问题。
但把它当作"已经安全了"是错的。

**根治方案（已设计，排在 M5 之后）**

识别命名管道客户端所属的会话，只放行**控制台会话**的用户与管理员：

1. `GetNamedPipeClientProcessId` 取得客户端 PID；
2. 打开该进程令牌，取出其会话 ID；
3. 与 `WTSGetActiveConsoleSessionId` 比对 —— 只有坐在物理控制台前的那个人
   才算数，远程桌面与后台服务一律拒绝。

这比"按 SID 白名单"更贴合语义，也不需要管理员预先配置谁被授权。
在此之前，文档必须如实说明该局限。

## D10 系统变更模型

**背景**　ISC 要改防火墙、装服务、绑端口、写证书。改系统 = 有副作用 = 有出事概率。同时存在验证闭环问题：改完之后 ISC 其实**不知道自己是不是真的通了**，因为验证必须从"外面"看；本机 `curl localhost` 永远成功，毫无意义。

**结论**　**计划 → 预览 → 应用 → 可回滚** + **引导式外部验证**。

- 所有系统级变更先产出人类可读的"变更计划"（要改什么、为什么、影响哪些端口），用户确认后才应用；
- 落库审计，支持一键回滚；
- 平台后端：Windows Defender Firewall（netsh / COM）、Linux nftables 为主并探测 ufw、macOS pf；
- **明确不碰**：系统代理、系统 DNS 设置、路由表、任何驱动；
- 验证闭环：应用后生成一次性验证链接，引导用户用手机 4G/5G 打开，结果回写数据库；不依赖第三方探测服务。

**理由**　服务以 SYSTEM / root 运行时，一个 bug 就是系统级事故。可预览 + 可回滚把"出错"从灾难降级为操作。

**后果**
- `internal/plan/` 是 M0 就要有的框架，不是 M3 才补。
- 每个平台后端都必须实现 `Plan() -> Change` / `Apply(Change)` / `Rollback(Change)` 三段式。
- 引导式验证需要一次性 URL 与回调，涉及一个短暂的本机监听端口。

## D11 平台推进策略

**背景**　防火墙后端、服务安装、IPv6 地址枚举、前缀变化监听在三个平台上是四套独立代码，macOS 的 pf 与 Windows Defender Firewall 无可复用性。

**结论**　**一套 Go 代码**（`GOOS` 条件编译），**三平台适配层同步做**。共享代码占比约 90%。

**澄清**　不存在"Windows 内核 / Linux 内核"两份代码。平台差异全部收敛在 `internal/platform/` 下的接口 + 每平台一个实现文件，用 build tag 切换。未实现的后端可降级为"引导模式"（告诉用户该放行什么，但不代其动手）。

**平台适配面**

| 接口 | Windows | Linux | macOS |
|---|---|---|---|
| `Firewall` | Defender Firewall (COM/netsh) | nftables（探测 ufw） | pf |
| `ServiceManager` | SCM | systemd | launchd |
| `IPMonitor` | `GetAdaptersAddresses` + 轮询 | netlink (`RTM_NEWADDR`) | `getifaddrs` + 路由 socket |
| `SecretStore` | DPAPI | Secret Service | Keychain |
| `Transport` | 命名管道 | Unix socket | Unix socket |
| `LowPortBinder` | 无限制 | `CAP_NET_BIND_SERVICE` | 无限制 |

**后果**
- 必须保持**纯 Go**（无 cgo），否则三平台交叉编译与 CI 复杂度爆炸。SQLite 选型即因此（D06）。
- 三平台始终保证 `go build ./...` 通过 —— 用 stub 实现兜底。
- 每个平台后端需要一套**一致性测试套件**，确保行为语义一致。
- macOS 无法在开发机验证，需要 GitHub Actions `macos-latest` + 真机/VM。

## D12 内核与 GUI 的边界

**结论**　内核**没有 GUI**，也不内嵌 Web UI 作为产品界面。内核只提供：完整接口面（OpenAPI）、CLI、以及一个**仅供验证**的浏览器控制台。

**理由**　产品 GUI 由项目所有者后续独立开发，内核只负责提供契约。这样内核可以完全独立演进而无需等待 GUI。

**后果**
- 内核不得包含任何产品级 UI 依赖。
- `--console` 提供的控制台明确标注为验证工具。
- 接口的稳定性与文档质量直接决定下游 GUI 的开发成本。

## D13 验证控制台形态

**结论**　**真·API 客户端 SPA**（Vite + React/Svelte + `openapi-typescript` 生成的客户端），走 HTTP + token，**不直接调用内核内部函数**。内核用 `--console` 开关提供，默认关闭。

**理由**　只有真正走 HTTP 层，控制台才能验证契约；否则等下游 GUI 接进来才发现接口不好用。它同时是契约的"活文档"：跑得通就说明 spec 与实现一致；其中的调用代码可被下游 GUI 直接复用。

**后果**
- 控制台代码不得 import 任何内核内部包。
- 控制台的构建产物需要嵌入内核二进制（`go:embed`）或由 `--console-dir` 指定。
- 控制台必须覆盖跨接口流程（配置 → 启动 → 验证可达），而不只是单接口调试。

## D14 反向代理与证书

**背景**　国内家宽普遍封 80/443，通常只剩**一个**可用非标端口。没有反代则一个端口只能对一个服务。而 DNS-01 证书校验正好需要 DNS 服务商凭据 —— 这个凭据 ISC 手里已经有了。

**结论**　内核**内置反向代理 + ACME DNS-01 自动 HTTPS**。

**理由**
- 家宽封 80/443 时，只用一个非标端口就能发布任意多个服务（靠 SNI / 域名路由）；
- DNS-01 不依赖 80 端口，是封端口环境下唯一可行的签发方式；
- 与 Tier-1 凭据天然咬合。

**后果**
- 反代实现基于标准库 `net/http/httputil.ReverseProxy` + `tls.Config.GetCertificate`，不引入 Caddy 的巨型依赖树。
- 证书管理用 `certmagic` + libdns 适配器。
- **安全约束**：严格限制上游地址（SSRF 防护）、禁止开放代理、清理转发请求头、禁止 CONNECT 转发。

## D15 Provider 抽象层

**背景**　`libdns` 的接口本身就是 CRUD（`ZoneLister` / `RecordGetter` / `RecordAppender` / `RecordSetter` / `RecordDeleter`），且 `certmagic` 原生消费该接口。但 libdns 的国内厂商 provider 多为社区维护、版本偏 beta（如 `libdns/alidns` 仍为 `v1.0.4-libdns.v1.beta1`），而 ddns-go 的国内厂商实现被海量用户验证过。GoDaddy 无官方 libdns provider。

**结论**　**自研 `dns.Provider` 接口 + 双向 libdns 适配器**。

- 自研接口能力模型参考 libdns，用 Capability 位声明支持的能力；
- Tier-1 手写，直接复用 ddns-go 的签名代码，**不押注 beta 库**；
- Tier-2 照搬 ddns-go；
- 另写一层双向胶水（约 200 行）：
  - 我们的 Provider → libdns（给 certmagic 用）；
  - libdns provider → 我们的接口（白捐 40+ 家 provider）。

**后果**
- 需要维护适配器的一致性测试。
- 引入 libdns provider 时需检查其许可证与 GPLv3 的兼容性（多数为 MIT，兼容）。
- 接口演进的主动权保留在自己手里。

## D17 仓库与许可证

**结论**　**GitHub 公开仓库 + GPL-3.0**，module 路径 `github.com/ShirazuNagisa/isc-core`。

## D18 通知与告警

**背景**　"把电脑当服务器"最怕的不是它坏，而是**它悄悄坏了你不知道**：前缀变了没更新、证书过期、端口被运营商封。而 ISP 重拨可能一天数次，不做去重就会刷屏。

**结论**　**多通道通知中心 + 去重静默**。

- 触发点：IP/前缀变化、解析连续失败、证书即将过期/续期失败、端口不可达、内核异常；
- 自带去重 + 静默期 + 频率限制。

**后果**
- 通知通道配置需加密存储（含 webhook 密钥 / SMTP 密码）。
- 需要通知历史与"已发送"状态去重表。

## D19 CLI 范围

**结论**　**完整 CLI + 交互式引导 + `--json`**。

**理由**　若无完整 CLI，M2 阶段验证 5 家 Tier-1 的 CRUD 只能靠手点控制台，无法进 CI、无法批量回归。

**后果**

## D20 数据目录与运行模式

**背景**　服务必须能在无人登录时运行（服务器的基本要求），且要能改防火墙、绑低端口。Windows 上用户级进程改防火墙每次都要弹 UAC。

**结论**　**系统级服务 + 标准系统目录**。

| 平台 | 配置 | 数据 | 服务 |
|---|---|---|---|
| Windows | `%ProgramData%\ISC\` | `%ProgramData%\ISC\` | Windows 服务（LocalSystem 或专用虚拟账户） |
| Linux | `/etc/isc/` | `/var/lib/isc/` | systemd |
| macOS | `/Library/Application Support/ISC/` | 同左 | launchd |

`runtime.json` 所在目录用 ACL 限定仅本机用户可读。日志：journald（Linux）/ 文件 + 事件流（Windows、macOS）。

**后果**
- `isc install` 需要管理员权限。
- 需要处理"服务账户与交互用户不同"导致的路径与权限问题。

  这一条以最容易被误读的形式出现过：内核以系统服务身份运行、数据在系统目录，
  而普通用户跑 `isc status` 时用的是自己的回退目录 —— 于是提示是
  "内核未运行。请先执行 'isc daemon run' 或安装为系统服务。"，而用户很可能
  **已经**装成系统服务了。两者指向完全不同的下一步动作，因此 CLI 现在会额外
  检查系统目录是否存在，并在存在时补一句"它可能在系统目录里，查看需要
  `sudo`"（见 `paths.SystemDataDir` 与 `internal/cli/root.go` 的 systemDirHint）。

## D22 验证控制台的鉴权模型与 DNS rebinding 防护

**背景**　M2-e 需要一个浏览器可访问的验证控制台。它带来两个别处不存在的问题：

1. 浏览器加载 HTML 页面时**无法**携带 `Authorization` 头。若静态资源要求鉴权，控制台永远打不开，而错误表现只是一个 401 空白页。
2. 网页可以发起跨站请求。正常情况下浏览器会因缺少 CORS 头而**阻止页面读取响应**，因此拿不到令牌 —— 但 **DNS rebinding** 可以绕过这一层：攻击者先让自己的域名解析到自己的服务器（页面成功同源加载），随后把这个域名重新绑定到 `127.0.0.1`，浏览器便认为目标仍是同源，从而**允许页面读取响应**。

**结论**　控制台静态资源与 `/v1/console/bootstrap` 为公开路径（`isPublicPath`），但整个本地管理接口套上一层 `LoopbackGuard`：**Host 头不是本机地址的请求一律 403**。

放行清单：`127.0.0.0/8`、`localhost`、`::1`、`[::1]`，以及 `isc.local`。

**理由**

- 控制台静态资源里**没有任何数据**，令牌也不在其中；公开它不泄露任何东西。
- 令牌通过 `/v1/console/bootstrap` 交付，该端点受 `LoopbackGuard` 与自身的 Host 二次校验保护。能通过这两关的只可能是从本机浏览器发出的请求。
- **这没有扩大暴露面**：D09 已记录"同一台机器上的其它进程本来就能读到 `runtime.json` 里的令牌"。把一个本机进程已经能拿到的东西交给本机浏览器，不构成新的攻击面。
- `LoopbackGuard` 是**唯一**能挡住 DNS rebinding 的一层：那种请求带着正确的令牌（如果令牌已经在页面手里），因此鉴权中间件拦不住；而它的 Host 头必然是攻击者的域名，所以校验 Host 是精确的堵法。
- 必须放行 `isc.local`：命名管道与 Unix 套接字没有真实 host，CLI 客户端统一用这个占位值（见 `platform.Endpoint.HTTPBaseURL`）。它不可能是公开可解析的域名。若不放行，整个 CLI 会失效 —— 而 CLI 是内核开发与运维全过程唯一的手和眼睛（D19）。

**后果**

- 通过局域网 IP、自定义主机名、或任何反向代理访问控制台都会得到 403。这是**有意**的：内核的管理接口只监听回环，任何其它来源的 Host 都只可能来自被伪装的请求。将来若需要远程访问，应当走一条独立的、有完整鉴权的通道，而不是放宽这个校验。
- 根路径 `/` 也必须公开，否则用户打开 `http://127.0.0.1:PORT/` 会看到一个 401 空白页 —— 而那正是他判断"内核起没起"的第一眼。
- 已实现的校验由 `TestConsoleRejectsForeignHost`（伪造 Host 必须 403 且响应里不含令牌）与 `TestConsoleAcceptsLoopbackHosts`（正常访问方式不得被误伤）双向守住。
- 静态资源缺失时返回 **404 而不是首页**。SPA 的"回退到首页"在这里是错的：它会让一个拼错的脚本路径变成"页面加载了但什么都不工作"，而浏览器控制台里只有一句 `Unexpected token '<'`。验证工具应当直接给出 404。

**遗留**　D09 的已知限制（令牌可被同机任意交互用户读取）依然存在，本决策不改变它。真正的修复仍是 R13 的会话级授权。

## D23 密钥条目的作用域

**背景**　D06 定的是"主密钥存进 OS 钥匙串"。而钥匙串里的条目名是**全局**的
（`service=isc-core`、`account=master`），内核的其余一切却都以数据目录为界。

这个不对称在 macOS / Linux 上是真实故障，不是理论问题：

1. **测试互相覆盖，并且会覆盖真实安装。** 测试各自建临时数据目录，却都往
   同一条全局条目上写。实测中 `go test ./...` 把登录钥匙串里的
   `isc-core/master` 写成了 9 字节的测试值（`TestCorruptedKeyIsRejected`
   故意写的 `"too short"`），于是**所有**以临时目录启动内核的端到端测试
   集体报"主密钥长度异常"；在一台装了真实内核的机器上，同样的机制会把
   用户的主密钥换掉 —— 那等价于把全部凭据变成解不开的密文。
2. **两个数据目录共用一把主密钥**，于是"密钥属于哪个安装"这件事没有定义。
3. 顺带暴露的另一处：不安全的名字（空、`..`、路径分隔符）在文件后端被拒绝，
   在钥匙串后端却被照单全收 —— 登录钥匙串里因此留下了
   `account="../../etc/passwd"` 这样的垃圾条目。

**结论**　钥匙串 / Secret Service 的条目名与数据目录绑定：
`<名字>@<数据目录指纹>`（指纹 = 数据目录绝对路径的 sha256 前 4 字节）。

- 读：先查绑定后的名字；没有则回退到旧的全局名字，并**尽力而为地搬一次家**
  （写到新名字上，成功后再删旧的）；
- 写：永远写到绑定后的名字上；
- 删：两条都删 —— 只删新的会让旧条目在下一次读取时被回退捡回来；
- 名称校验（`validateKeyName`）对**所有**后端生效，不再只是文件后端。

**理由**

- 迁移安全优先于整洁：旧条目必须仍然读得到，否则升级之后内核会认为
  "没有主密钥"并生成新的一把，用户已有的全部凭据当场作废。因此回退是
  读路径的硬要求，而写路径必须立刻切到新名字，避免继续产生全局条目。
- 指纹取绝对路径的哈希而不是路径本身：条目名要短、要稳定，且不该把用户的
  目录结构写进钥匙串。相对路径与绝对路径归一化到同一个指纹（内核可能以
  不同的工作目录启动，那不该改变"密钥住在哪"）。
- 失败时的取舍：搬家失败**不影响这次读取**（值已经在手上），只是这台机器
  会继续从旧条目读 —— 可用性优先于整洁。

**后果**

- 移动数据目录会失去与旧密钥的关联（旧条目在没有回退时读不到）。这是**有意**
  的：密钥本就属于那个目录。真要迁移，走 YAML 导出导入（D06）。
- `internal/platform` 上新增四条测试守住它：同值同指纹/异值异指纹、
  两个数据目录互不可见、旧条目仍被读到并搬家、删除会清掉两条。
  前两条在绑定之前**必然失败**。
- 未实现（已知）：CLI 后端在**运行时**不可用（钥匙串被锁、无桌面会话）时
  仍会直接报错，`cliSecretStore.fellBack` 这个字段至今没有被置位过 ——
  "降级到文件存储并明确告警"目前只覆盖"启动时就没有这个工具"这一种情形。

  **而"运行时失败就降级"这个直觉是错的**，值得写下来免得有人顺手补上：
  主密钥只存在钥匙串里，文件存储里没有副本。此时若降级，`Open` 会认为
  "没有主密钥"并**生成一把新的**，于是数据库里所有用旧密钥加密的凭据
  永久解不开 —— 用户会看到一个能启动、能登录、却每一条凭据都报错的
  内核。**报错才是正确行为**，需要改进的只是错误信息要可行动
  （说清"钥匙串不可用"以及可用 `ISC_SECRET_STORE=file` 的场合）。

## D24 内核的可调用库化（与 GUI 的嵌入方式）

### 背景

项目主修正了内核的定位：**内核的交付形态是"可调用库"**，GUI 嵌入它来实现
功能；`isc daemon` 与 `isc` CLI 只是库的**第一个消费者**。v0.1.0 的验收口径
也随之收窄为"**在这台 Mac 上功能全部可用、无已知问题**"。

这与仓库里既有的两处判断直接相关，必须先摆清楚，不能默默实现：

1. **R7（许可证红线）**：内核是 GPL-3.0。**链接**内核的 GUI 会被 copyleft
   覆盖 —— 也就是说 GUI 必须以 GPLv3 兼容许可发布。R7 当初的对策正是
   "GUI 只走 HTTP/WS，禁止链接内核"。
2. **纯 Go / 无 cgo 约束**：现有全部代码不依赖 cgo（`CGO_ENABLED=0`）。

### 三条技术路线与各自的硬约束

| 路线 | 形态 | 约束与代价 |
|---|---|---|
| **A. Go 包导入** | GUI 是 Go 程序（如 Wails），直接 `import` 内核包 | 最省事：无 cgo、无 IPC、进程内直调。**但**现有代码几乎都在 `internal/` 下 —— 外部模块无法导入，需要把稳定面提升为公开包（`pkg/...`）。GUI 必须是 Go |
| **B. c-shared 动态库** | `go build -buildmode=c-shared` 产出 `libisc.dylib` / `.dll` / `.so` + 头文件，Rust/Tauri、Swift、C# 等经 FFI 调用 | 真正的"嵌入"。**但**：① `c-shared` **必须开 cgo**，与现有约束冲突；② 每个目标平台都要 C 工具链（本机没有 MSVC 链接器）；③ 需要设计一套稳定的 C ABI（生命周期、回调、字符串所有权、panic 不得穿过边界）—— 是独立的一块工程量 |
| **C. sidecar + 客户端库** | 保持现状（进程 + Unix 套接字 + `runtime.json`），把"可调用库"理解为**给 GUI 的客户端库**（封装连接、事件订阅、错误映射） | 无 cgo、无许可证传染（进程边界不构成链接）。代价是"嵌入"是进程级的：GUI 要管进程生命周期，或将内核注册为系统服务 |

### 影响与要做的事（无论选哪条）

- **公开 API 面**：生命周期（启动/停止/等待就绪）、状态与健康、配置读写、
  凭据存取、事件流（状态变化、IP 变化、证书签发结果）、错误类型与错误码。
  这些现在大多只通过 CLI/HTTP 暴露，需要评估哪些直接可用、哪些要重做。
- **库的契约测试**：现在 780 条测试基本都是"包内视角"。库化之后需要一组
  **面向调用方**的测试：从外部模块导入、按文档调用、断言行为 —— 否则
  "能编译"与"能用"之间会留一条今天见过的老路（自己的测试与实现共享同一套
  假设）。
- **不再以"独立应用的打包"为重心**：`.deb` / `.rpm` / `.msi` / `.pkg` 仍然
  有用（把内核作为服务分发），但它们**不再是 v0.1.0 的验收内容**。

### 已决定（2026-10-03）

1. **技术栈**：GUI 在 macOS 上用 **Swift**、Windows 上用 **C#**，均为原生语言
   → 路线定为 **B（c-shared / C ABI）**，已在本机跑通（见下面的补记）。
2. **许可证**：**GUI 同样以 GPLv3 开源** ✓。
   → 链接内核库不构成许可证冲突，**不需要**任何例外或双许可；
   内核保持 GPL-3.0，GUI 以 GPLv3 兼容许可发布即可。
   R7 那条红线（"GUI 只能走 HTTP/WS，禁止链接内核"）因此**不再适用**：
   它防的是"闭源 GUI 链接 GPL 内核"，而现在的选择是 GUI 也开源。
3. **已知偏差的处理**：pf 的启用状态在撤销后不恢复（见 `ACCEPTANCE-macos.md`）
   —— 经评估**影响很小**（规则本身撤销干净、anchor 挂载点是有意保留、
   多一个已启用的 pf 在只有 Apple 默认规则时几乎无副作用），
   **暂不修改**，作为已知偏差记录在案。
4. **发布产物只有可链接的库**（2026-10-03）：`.deb` / `.rpm` / `.pkg` / `.msi`
   与各平台归档**不再进发布**，发布 = `libisc.dylib`（Windows 上 `isc.dll`）
   + 头文件 + `SHA256SUMS`，由 `scripts/build-libisc.sh` 产出。
   打包代码保留在 `scripts/release`（自己分发时仍可用），但不再是交付物 ——
   这与"内核的交付形态是可调用库、GUI 是唯一消费者"这条定位一致：
   守护进程与 CLI 只是库的一个消费者，不该再被当成独立产品分发。

### D24 补记（2026-10-03）：路线 B 已跑通，并记下三个坑

项目主明确了 GUI 的技术栈：**macOS 用 Swift、Windows 用 C#**，两者都只链接
**功能接口**。能同时被这两种语言链接的只有 C ABI，因此路线定为 **B（c-shared）**，
并且已经在本机跑通：

| 产物 / 组件 | 说明 |
|---|---|
| `cmd/libisc` | c-shared 目标，带 `//go:build cgo` 标签（**唯一**要求 cgo 的地方） |
| `scripts/build-libisc.sh` | 构建 `libisc.dylib` + 头文件；Windows 上是 `isc.dll` |
| `examples/swift-smoke/` | Swift 冒烟测试：链接库 → 进程内启动内核 → 读状态 → 停止 |
| CI `libisc-macos` | 在 macOS runner 上重复上面这条链路，并检查 6 个导出符号齐全 |

**实测证据**（本机 macOS arm64，Swift 6.4 / clang 21）：`swiftc` 链接
`libisc.dylib` 成功；内核在 Swift 进程内启动，返回 `health = ok`、
`version`、以及六个后端（pf / polling / darwin-native / macos-keychain /
launchd / unix-socket）；停止幂等。复跑：`examples/swift-smoke/run.sh`。

#### 接口形状：JSON 进 / JSON 出

结构体跨语言传递会引入 ABI 对齐与版本漂移；JSON 两端都稳，而且内核已有的
API 面（`internal/api`，版本 v1，有 openapi 契约与 spec-drift 检查）本身就是
JSON。因此库只是把**同一条路径**搬进进程内 —— GUI、CLI、控制台看到的行为一致，
不会出现"库一套实现、CLI 另一套"。

#### 三个坑（都已修，记下来是因为它们会再出现）

1. **DNS rebinding 防护拦下了自己的请求**：第一版把 Host 写成 `isc`，内核
   如实拒绝（`拒绝非本机 Host 的请求`）。**改的是调用方**（用 `127.0.0.1`），
   不是去放宽内核 —— 那层防护挡的是浏览器发起的跨站请求。
2. **猜接口路径拿到 404**：写了 `/v1/status`，而契约里没有这个路径。库的功能
   面必须**对着 `api/openapi.yaml` 写**，不能凭印象。这也是"库的接口 = 契约的
   路径"这条设计的现实理由。
3. **`dyld: Library not loaded`**：c-shared 默认把 install name 写成**裸文件名**，
   于是链接它的程序运行时找不到库、rpath 也不生效。构建脚本里显式设成
   `-Wl,-install_name,@rpath/libisc.dylib` —— GUI 打包时库要放进
   `Contents/Frameworks/`，正是靠 `@rpath` 定位。

#### cgo 的边界（已验证不破坏既有约束）

只有 `cmd/libisc` 需要 cgo，且用 `//go:build cgo` 隔离：`CGO_ENABLED=0` 下
`go build ./...`、`go vet ./...`、`go test ./...` 与发布矩阵**全部照常**
（22 个包全绿）。内核本体、CLI、守护进程仍然零 cgo。

注意一个行为差异：开 cgo 构建时 `net` 包可能改用系统解析器。若要确定性，
可在库的构建里加 `GODEBUG=netdns=go` 或 `netgo` 标签 —— 目前未加，先记录。

#### 2026-10-03 第二轮：初步封装完成

接口面从"四个函数"扩到**可用的一版**，并且验证方式也补上了：

| 接口 | 说明 |
|---|---|
| `isc_api_version` / `isc_version_json` | 版本与接口版本（GUI 启动时先比对接口版本） |
| `isc_start` / `isc_stop` / `isc_restart` | 生命周期；启动阻塞到**完全就绪**，停止幂等 |
| `isc_status_json` | 便捷：`health` + `meta`（含六个后端的能力与后端名）合成一份 |
| `isc_call(method, path, body)` | **核心**：进程内派发到契约里的任意路径（38 条），新增功能**不用改库** |
| `isc_events_json(since, timeoutMs)` | 事件订阅：游标式长轮询（**不用 C 回调**，见下） |
| `isc_free_string` | 内存所有权归调用方，每个返回值都要释放 |

**错误码**（`code` 字段）是这一轮补上的关键一项：GUI 要按错误分支，而不是匹配
文案（文案会随语言变）：`bad_request` / `unauthorized` / `forbidden` /
`not_found` / `conflict` / `not_running` / `not_ready` / `already_running` /
`timeout` / `internal`。

**分层**：行为全在 `internal/libisc`（不依赖 cgo → **默认 CI 就覆盖**），
`cmd/libisc` 只是 cgo 薄包装。这么分是被工具链逼出来的：Go 不允许在
`_test.go` 里 `import "C"`。测试覆盖生命周期、通用调用、错误码、事件游标，
并且**不改开发机的状态**（凭据存储固定成文件后端）。

**为什么事件用长轮询而不是 C 回调**：回调要跨语言、跨线程，还要约定谁负责释放
内存，出错的方式比轮询多得多；GUI 本来就有自己的主循环，在后台线程里轮询更简单
也更安全。`gap=true` 表示事件曾因积压被丢弃，此时应当重新全量拉状态，而不是
试图补齐。

#### 仍未解决

1. **许可证**：Swift/C# GUI **链接**这个库即构成衍生作品，GPLv3 会覆盖 GUI
   （R7）。要么 GUI 也以 GPLv3 兼容许可发布，要么由作为著作权人的项目主
   给出**明确的例外/双许可**。这件事不影响构建，但决定能否发布闭源 GUI。
2. **最终 API 面**：目前只有版本 / 启动 / 状态 / 停止四个函数。要覆盖生命周期、
   配置读写、凭据、事件订阅（状态变化、IP 变化、证书结果）、以及错误类型。
   设计时遵守两条：**路径与语义对齐 openapi 契约**、**字符串统一走 i18n**
   （项目已有的守门测试会检查后者 —— 它当场就抓到了本库的 11 处硬编码中文）。
3. **Windows 端未验证**：本机没有 .NET，也没有 MinGW/MSVC；`isc.dll` 的构建与
   C# `[DllImport("isc", CallingConvention = CallingConvention.Cdecl)]` 要在
   Windows 机器上验。

## D25 内核托管业务服务生命周期

**日期**：2026-10-04
**状态**：已决定（**推翻 D01 的结论部分**）

### 背景

ISC Phecda v0.2.0 的产品定位收窄到一个具体场景：**面向只想"一步到位"的用户，
把网站源码变成可公网访问、带 SSL 的服务**。目标用户不装运行时、不敲命令行、
不配置反向代理。

按 D01，这部分被明确划在核心里之外：

> `**结论**　ISC 是**接入编排器**：只负责"让外部能访问到本机"。业务服务（Jellyfin / Minecraft / nginx / SSH）由用户自行安装，ISC 不托管其生命周期。`（`:47`）
> `- 内核不提供"一键安装应用"能力；GUI 阶段也不做。`（`:52`）
> `- 端口/防火墙/证书/反代属于内核职责；进程守护业务服务不属于。`（`:54`）

D01 给出的理由是：

> `**理由**　托管业务服务（应用市场 + 服务管理器）的跨平台差异极大，工作量翻 2~3 倍，且会把项目拖入与 1Panel / 宝塔的同质竞争…`（`:49`）

PHECDA-INTEGRATION 阶段把这个划分进一步落成实现：运行时下载、依赖安装、构建、
进程/容器生命周期、健康检查、日志、端口、恢复全部归 Phecda Supervisor
（`docs/PHECDA-INTEGRATION.md:21–25`、`:80`），并且被写进了代码注释与契约描述
（`internal/api/phecda.go:14–16`、`api/openapi.yaml:342`）。

v0.2.0 与这条决策正面冲突：要让用户"选个目录就上线"，上述能力就必须在内核里。

### 结论

**推翻 D01 的结论部分**。自 v0.2.0 起，内核负责业务服务的完整生命周期：

- 运行时（Node / Python / PHP / Go / Java / .NET）的探测、下载、校验、解压与本地缓存；
- 依赖安装与构建；
- 进程守护：启动、停止、重启策略、健康检查、日志采集、端口分配、崩溃恢复；
- 与公网能力的绑定（DDNS 记录、反向代理规则、ACME 证书、可达性验证）。

**D01 仍然成立的部分**：内核不做应用市场、不做模板生态、不做集群调度；
`purpose=gameServer` 只保留字段，v0.2.0 不提供游戏预设。

### 理由

1. **产品定位优先于分层洁癖**。D01 拒绝"一键安装"的理由是"工作量翻 2~3 倍"与
   "同质竞争"——前者是成本判断，后者是市场判断，两者都不构成"能力必须放在
   GUI 侧"的技术理由。而把能力放在 GUI 侧（现状）已经产生了实际代价：
   Swift 侧独立维护了一套下载/校验/解压/进程守护实现，内核与它之间出现了
   **三处状态存储**与引用悬空问题，且这些能力无法被 CLI、控制台或未来的
   C# GUI 复用。
2. **跨平台差异由既有机制收敛**。D11 已经确立了 `internal/platform/`
   "接口 + 每平台一个实现文件 + stub 兜底"的模式，进程控制直接复用该模式即可，
   不需要新的架构。
3. **能力归属决定复用面**。放进内核后，同一套实现同时服务 GUI、CLI 与控制台；
   放在 GUI 侧则只有 GUI 能用。

### 后果与约束

- 内核的职责范围显著扩大，**进程守护与下载是本仓库历史上最大的一块净新增能力**
  （现状：无任何长期守护的子进程、无下载器、无解压、无指标采样，见审计）。
- 安全边界随之扩大：内核开始执行用户提供的源码所衍生的构建/启动命令。
  对应的边界由 **D30** 单独规定。
- 必须补齐：`internal/platform` 的进程抽象、`paths` 的缓存目录、以及
  `internal/job` 的若干缺口（它此前只有 `debug.noop` 一个生产消费者）。
- `docs/PHECDA-INTEGRATION.md`、`internal/api/phecda.go` 的注释、
  `api/openapi.yaml` 的相关描述**必须同步改写**，否则代码与文档互相矛盾。

## D26 进程模型与引擎的可分离性

**日期**：2026-10-04
**状态**：已决定（澄清 D03 与 D24 的关系）

### 背景

D03 要求内核是**独立守护进程**，理由之一是"GUI 崩溃或关闭不影响 DDNS 定时任务
—— 服务器场景的硬要求"（`:85`），并明确"禁止把内核作为 Go 库链接进任何 GUI"
（`:93`）。D24 选择了路线 B（c-shared / C ABI），内核以库的形式被 GUI 在
**本进程内**启动（`internal/libisc/libisc.go:139` `Start` 的注释："在**本进程内**
启动内核"），D24 同时声明 R7 红线不再适用（`:592`）。

两者在"进程形态"上并未正式对齐，v0.2.0 必须给出明确答案。

### 结论

1. v0.2.0 **沿用 D24 的进程内嵌**：内核由 GUI 通过 `isc_start` 在 GUI 进程内启动，
   GUI 注册为登录项实现开机自启。退出 GUI 即停止内核与全部业务服务，
   **不安装任何特权组件、不要求管理员密码**。
2. **部署引擎不得假设自己与 GUI 同进程**：不得依赖 GUI 的 Swift 对象、
   不得依赖进程内的临时状态；所有需要跨重启保持的状态必须落 SQLite 或数据目录。
   这样将来把内核改挂到用户级后台代理时，引擎无需改动。
3. v0.2.0 **不引入**系统服务安装路径（既有 `/v1/service/*` 与 root 级
   LaunchDaemon 保持可用但不在 GUI 中出现）。

### 理由

- 面向非专业用户的产品不应该在首次启动就要管理员密码；而 D03 设想的
  "安装时一次性提权"在"下载即用"的分发形态下没有安装时机。
- 进程内嵌已经跑通并被 9 个 C 函数固定下来（D24 补记），改回独立进程会同时
  推翻 D24 与整个 GUI 的连接方式。
- 把"引擎不假设同进程"写成硬约束，使后续切换到后台常驻成为**增量**而非重写。

### 后果与约束

- D03 的"独立守护进程"结论**在本版本不生效**；但 D03 对可靠性的关切被记录为
  已知取舍：退出应用即停止站点。产品文档必须明示这一点，不得让用户误以为
  站点会 7×24 运行。
- 单实例限制（`LIBRARY-API.md:155–156`：一个进程只能有一个内核实例）继续成立，
  `daemon.cleanupStaleRuntime` 的行为不变。
- 内核整体的关闭预算仍是 10s（`daemon.go:62`）。**业务进程的终止必须自带
  内部超时**，不得依赖该 drain 预算（见 D25 后果）。

## D27 契约破坏性变更与接口版本 v2

**日期**：2026-10-04
**状态**：已决定

### 背景

`internal/version/version.go:29` 定义 `APIVersion = "v1"`，注释写明它与内核版本
解耦、"只在出现破坏性变更时递增"。`docs/LIBRARY-API.md:71` 要求 GUI 启动时比对它。

v0.2.0 会**删除** `/v1/phecda/*` 与 `/v1/public-services`，并以
`/v1/apps`、`/v1/presets`、`/v1/sources/inspect`、`/v1/runtimes`、`/v1/metrics`、
`/v1/advisories` 取代。这是接口面的破坏性变更。

同时需要澄清一个容易混淆的点：**C ABI 本身不需要任何改动**。
`cmd/libisc/main.go:28–30` 与 `docs/LIBRARY-API.md:83–84` 都已写明
"新增功能不需要动库"——`isc_call` 是通用派发，功能面由契约定义。

### 结论

- `APIVersion` 递增为 **`"v2"`**；GUI 的启动校验从 `== "v1"` 改为 `== "v2"`。
- 9 个 C 函数**一个都不变**，`libisc.h` 保持逐字节不变。
- v2 与 v1 之间**不提供兼容层**：`/v1/phecda/*` 与 `/v1/public-services` 直接移除。
  依据是消费者唯一（Phecda GUI），且 Phecda v0.1.0 未公开发布（仓库无 tag），
  没有需要兼容的在野客户端。

### 理由

- `isc_api_version` 存在的意义就是让"GUI 配到了错误的库"变成一个明确的启动期
  错误，而不是运行期的 404。删除接口正是它应该拦下的情形。
- 保留废弃接口会让契约面永久背上无人调用的路径，而本项目的契约纪律
  （D07 + `make check-gen`）恰恰以"契约即产品面"为前提。

### 后果与约束

- `Vendor/ISC` 必须整体重新出包（`libisc.dylib` + `libisc.h` + `SHA256SUMS`），
  并更新 `Documentation/SDK.md` 中记录的摘要。
- 旧 SQLite 表（`phecda_projects`、`phecda_deployments`、`phecda_scan_evidence`、
  `public_services`）**保留不删**：删除是破坏性的且没有收益，迁移文件一旦发布
  也不可修改（见 `ARCHITECTURE.md:313`）。它们只不再被接口服务。
- `docs/LIBRARY-API.md` 的接口面清单需要按 v2 更新。

## D28 运行时供给策略

**日期**：2026-10-04
**状态**：已决定（项目主确认：检测优先 + 第三方预编译包）

### 背景

"装完即用"要求内核能自己把建站环境准备好。各语言在 macOS 上的可获取形态差异很大：

- **有官方预编译产物**：Node、Go、Java（Temurin）、.NET；
- **没有官方预编译产物**：PHP、Python（官方只发源码包，现场编译需要
  Xcode 命令行工具且耗时数分钟到十几分钟）。

现状（Swift 侧 `OfficialRuntimeManifest.swift`）下载的正是 Python 与 PHP 的
**源码包**，属于第 3 类做法，与"开箱即用"直接冲突。

### 结论

**三级解析顺序**，逐级回退：

1. **系统已装的解释器**：`exec.LookPath` 探测 + 版本解析，满足预设声明的最低版本
   即采用，标记 `source: system`，不下载任何东西；
2. **已供给的托管运行时**：数据目录下的标记文件（`.isc-runtime.json`）命中即复用；
3. **下载预编译发行版**：按**内置固定清单**（URL + SHA-256 + 体积 + 归档名 + 版本）
   下载并校验，标记 `source: managed`。

**首次启动的预取范围**：只预取小体积集合（Node / Python / PHP），
Go / Java / .NET 在发布向导中带**明确体积提示**按需下载。
默认集合可由设置 `default_runtime_kinds` 调整。

**PHP 与 Python 采用成熟的第三方预编译发行版**（而非官方源码包），
版本与摘要固定在代码常量中。

### 理由

- 检测优先让"机器上已经有了"的用户**零下载**，这是最常见也最省事的一档。
- 内置清单而非远程清单：可审计（摘要随代码 review）、离线可发布、
  不依赖任何外部清单服务的可用性。远程刷新留待后续版本。
- 预取范围按体积切分：Node+Python+PHP 合计约 100MB 量级，而 Go+Java+.NET
  合计约 500MB 量级。首次启动静默拉 500MB 对家用带宽不友好，
  放在用户已表达意图（选中某个预设）之后再下载更合理。

### 后果与约束

- **新增第三方发行版依赖**，其许可与声明义务由 D29 规定。
- `paths` 需要新增缓存目录（下载中转）与运行时目录，权限与 `run/`、`secrets/`
  同级收紧（0700；Windows 侧 ACL）。
- 下载与解压必须是安全实现：仅 HTTPS、边写边算 SHA-256、失败即删除、
  **拒绝路径穿越与逃逸符号链接**、先 staging 后原子改名、预检磁盘空间。
- 运行时内容视为**不可信输入**。

## D29 再分发运行时的许可登记

**日期**：2026-10-04
**状态**：已决定

### 背景

`THIRD_PARTY_NOTICES.md:5` 的规则是"新增任何依赖前，必须确认其许可证与
GPL-3.0 兼容，并在本文件登记"，但该文件目前只覆盖 **Go 模块依赖**（18 个，
已审计）。v0.2.0 会在用户机器上下载并解压整份语言运行时——**这是再分发**，
现有规则没有对应条款，也没有任何一份文档讨论过 Node / Go / Python / PHP /
Temurin / .NET 的再分发许可。

另有一处独立缺口：`ISC-Phecda/Documentation/SDK.md:11` 与 GUI 关于页都声明
GPLv3，但 **ISC-Phecda 仓库没有 LICENSE 文件**。

### 结论

1. `THIRD_PARTY_NOTICES.md` 新增**「再分发的运行时」**章节，逐个登记：
   名称、版本、下载来源、许可证、以及是否需要随附声明文件。
2. 运行时的许可证兼容性判断与 Go 依赖同等对待：**不兼容的一律不进清单**。
3. **ISC-Phecda 补 `LICENSE`（GPLv3 全文）**，与 D24 的决定（GUI 同样以 GPLv3
   开源）保持一致。

### 理由

- 下载到用户机器上的整份运行时在实质上等同于分发该软件，声明义务不能省略。
- 项目已经因为"缺一份声明"写过规则（ddns-go 的 MIT 声明是硬要求，D17 `:378`），
  把同一标准应用到运行时是自洽的。

### 后果与约束

- 新增或升级任何运行时条目时，必须同时更新该章节；这成为运行时清单的
  **准入条件**，与版本号、SHA-256 同级。
- Java（Temurin，GPLv2 + Classpath Exception）与 PHP（PHP License 3.01）
  需要单独确认其声明形式。

## D30 业务进程的执行与隔离边界

**日期**：2026-10-04
**状态**：已决定

### 背景

内核开始执行构建与启动命令后，"内核会不会执行任意代码"成为一个必须写清楚的
边界。现状并不干净：`internal/ddnsgo/ipsource.go:250–257` 已经会通过
`powershell` / `bash -c` / `sh -c` 执行**用户配置的命令**来获取 WAN IP。
也就是说"内核从不执行用户命令"今天已经不成立。

Swift 侧 Supervisor 的立场值得沿用（`Docs/PhecdaSupervisor.md:39–45`）：

> `Only existing PresetCommand values are accepted; this boundary never invokes a shell or accepts free-form executable paths/arguments. … this is a **trusted local client** boundary, not a sandbox for untrusted projects.`

### 结论

1. **预设命令是固定 argv 数组，不经 shell**。可执行文件与参数由内核常量表给出，
   接口不接受自由形式的路径与参数。
2. **自定义服务器**允许用户提供可执行文件与参数数组，但：
   - 仍然**不经 shell**（不拼接字符串、不调用 `sh -c`）；
   - 接口要求显式确认字段（`confirm_custom: true`），GUI 必须二次确认；
   - 命令落入应用记录并可审计。
3. **子进程环境变量最小化**：只传显式白名单（`PATH` / `HOME` / `LANG` / `TMPDIR`）
   加上用户为该应用声明的变量，**不继承内核进程的环境**，避免内核的令牌与
   密钥被业务进程读到。
4. 定性上沿用 Supervisor 的表述：这是**可信本地客户端**边界，不是沙箱；
   业务进程以当前用户身份运行，与用户自己敲命令等价。

### 理由

- 不经 shell 消除了一整类注入与引号转义问题，且预设命令本来就不需要 shell
  特性（管道、通配、重定向）。
- 环境变量最小化是低成本高收益的一条：内核进程里存在访问令牌，
  让它出现在用户网站的进程环境里没有任何正当理由。

### 后果与约束

- "自定义服务器"必须仍然可用（产品要求：预设覆盖不到时能高度自定义），
  因此边界靠**显式确认 + 不经 shell + 环境最小化**来守，而不是靠禁止。
- `internal/ddnsgo/ipsource.go` 的既有 shell 路径**不在本次范围内**，但应记录
  为已知的不一致，后续按同一策略收敛。
- 内核自身监听的套接字不随子进程继承（Go 默认 CLOEXEC），此点需在实现中确认。

## D31 关闭 R7 悬置

**日期**：2026-10-04
**状态**：已决定

### 背景

D17 曾立下一条架构红线：

> `3. ⚠️ **架构红线**：下游 GUI 通过 HTTP/WS 与内核通信，是两个独立进程，通常不构成衍生作品，GUI 可自选协议。**若把内核作为 Go 库链接进 GUI，整个 GUI 将继承 GPLv3。** 此红线必须写入 README。`（`:380`）

D24 已决定 GUI 同样以 GPLv3 开源，并明确该红线不再适用（`:592`）。
但仓库里仍有两处按旧结论书写的文字没有清理：

- `PLAN.md:24` 仍把"许可证边界（R7）"列为**仍待决定**；
- `PLAN.md:2824` 的风险登记仍写"架构红线写入 README：GUI 只能走 HTTP/WS，
  **禁止链接内核**。**2026-10-03 起与 D24 冲突**…"；
- `README.md` 的许可证段与 `ARCHITECTURE.md:606` 的安全清单条目仍宣称
  "禁止把内核作为 Go 库链接进任何 GUI"。

而实际交付的产品（Phecda 链接 `libisc.dylib`）早就不符合这三处文字。

### 结论

**以 D24 为准关闭 R7**：GUI 以 GPLv3 兼容许可发布即满足要求，不存在未决的
许可证问题。同步清理上述三处失效文字，使其与 D24 一致。

### 理由

- 一条被产品实际行为违反、且已被后续决策推翻的记录留在"仍待决定"里，
  比没有记录更糟：它会让后续读者以为存在一个尚未处理的阻塞项。
- 决策记录的权威性依赖于"当前结论唯一"。允许互相矛盾的条目长期共存，
  等于取消了 ADR 的作用。

### 后果与约束

- `README.md`、`docs/ARCHITECTURE.md`、`docs/PLAN.md` 三处必须与 D24 对齐。
- ISC-Phecda 需要实际附上 `LICENSE`（与 D29 同一项工作），
  否则"以 GPLv3 发布"只是口头声明。
