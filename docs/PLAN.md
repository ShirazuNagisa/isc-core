### M2-d 的实施方式与结果

Tier-1 六家的实现是**并行委托给五个子代理**完成的，每个代理拿到：
接口定义、参考实现（Cloudflare）、参考测试、以及**移植代码里的真实
API 用法**（`internal/ddnsgo/provider_*.go`）作为端点与签名的依据。

结果与预期一致的部分：五家都独立完成了完整 CRUD、零新增依赖、
测试全部通过。

**超出预期的部分更值得记下来** —— 三个子代理主动否决了我的指示：

1. **DNSPod 那家拒绝了我给的 TTL 说法。** 我在任务书里写"TTL 只接受
   特定几个值"，它去查了官方文档后指出那是**区间**（1–604800 + 套餐
   最小值）而非档位表，并按文档实现。它是对的：按档位取整等于静默
   改数据（900→1800）。
2. **华为云那家纠正了我的端点版本。** 我写的是 `/v2/...recordsets`，
   它核对官方文档后确认记录集那一族是 **v2.1**（域名列表仍是 v2），
   并在注释里标明"两个版本并存不是笔误"。
3. **DNSPod 那家指出"没有只读校验端点"这个理由对 DNSPod 不成立** ——
   `Info.Version` 是可用的。它没有借这个理由糊弄过去，而是如实说明
   "当前未接，需要的话可以加"。

三家都主动报告了自己**没有**验证的假设（分页游标形态、权限副作用、
weight 丢失），并且都没有粉饰。这些已全部进 `docs/PROVIDER-MATRIX.md`
的「已知限制与未验证项」。

### M2 真机验证抓到的三个问题

这三个都是**只有跑在真实机器上才会暴露**的，单元测试的构造数据里不会出现：

1. **`/128` 主机路由被当成了委派前缀。** Windows 把 IPv6 主机地址报成 `/128`，
   而隐私扩展地址默认**每小时轮换**。若不区分，内核会每小时检测到一次
   "前缀变化"并触发全量更新 —— 白白消耗服务商配额，用户还会收到莫名通知。
   修法：只把 `/64` 及更粗的前缀视为委派网段（`isDelegatedPrefix`）。
2. **虚拟网卡识别靠英文名称前缀，在中文 Windows 上完全失效。**
   真机上出现了 `蓝牙网络连接`、`本地连接* 1`、`VMware Network Adapter VMnet1`
   （以 `VMware` 开头，不是 `vmnet`）。修法：改用"有没有可用地址"作为
   主判据（`HasUsableAddress`），名称列表退为辅助 —— 语言无关。
3. **`primary_ipv4` 取了第一个 IPv4，而真机上第一个是 `169.254.x`（APIPA）。**
   把自分配地址当成"当前公网地址"展示会直接误导用户。
   修法：只取非链路本地、非私有的地址。



本机没有 MSVC 工具链。为保证三平台交叉编译与 CI 简单可靠，**内核禁止引入任何需要 cgo 的依赖**。这直接决定了：

- SQLite 选 `modernc.org/sqlite`（纯 Go），而不是 `mattn/go-sqlite3`；
- `SecretStore` 走系统 API 调用（`golang.org/x/sys/windows`、`syscall`），而不是链接 libsecret 等 C 库；
- CI 中加一道检查：`CGO_ENABLED=0 go build ./...` 必须通过。

**代价（必须知晓）**：`go test -race` 需要 cgo，因此**开发机上跑不了竞态检测**。
处置方式：CI 在 Linux / macOS 上用 `CGO_ENABLED=1` 单独跑一组 `-race` 测试 ——
只影响测试，不影响发布产物的构建形态。见 `.github/workflows/ci.yml` 的 `race` job。

### M3 闭环：把已经写好的三块接起来

上一轮结束时有一个**真实缺口**：`reach.Plan`、`change.Runner.Apply`、
`change.Runner.Rollback` 都实现了，但**没有任何接口能调用它们** ——
M3 验收标准的第 1、2 条因此无法满足。

#### 核心设计问题：计划里含闭包

"预览 → 应用"要求用户先看到差异再决定，但计划里的步骤持有
`apply` / `revert` 闭包（它们捕获了平台后端的句柄），那些东西既不能
序列化，也不能通过 HTTP 传一个来回。

解法：内核生成计划后**留在内存里**，只把可序列化的预览发给客户端；
用户确认时凭 plan ID 回来取。计划取出即消费，因此双击"应用"不会
执行两次。

更重要的原因是安全：若改成"客户端把计划传回来"，就等于让客户端能
构造一份计划让内核**以管理员身份执行任意防火墙操作**。留在内存里
天然没有这个问题。

计划 10 分钟过期。这也是刻意的：预览里的差异是基于**当时**的系统状态
算出来的，放太久之后状态可能已经变了，那时再应用会让实际效果与用户
看到的差异不符。

#### 真机上抓到的体验缺陷

首次跑通闭环时，用户看到的是一整屏 CLIXML XML：

```
❌ 变更失败，已自动回滚到执行前的状态。
     原因：platform: 执行防火墙命令失败: #< CLIXML
<Objs Version="1.1.0.1" xmlns="http://schemas.microsoft.com/powershell/2004/04">
<Obj S="progress" RefId="0">...<S S="Error">New-NetFirewallRule : Access is denied. ...
```

当 stderr 被重定向时，Windows PowerShell 会把错误写成 CLIXML。那段输出
**看起来像内核崩了**，而实际问题只是缺管理员权限。

修法：抽出 `<S S="Error">` 的内容、还原 PowerShell 的 `_xHHHH_` 转义、
丢掉定位行。关键是**按位置截断**而不是逐节点过滤 —— 长行会被折成多个
节点，逐节点过滤会把续行片段（`tFirewallRule], CimException`）留下来。
真机上第二次跑才暴露这一点。

修复后：

```
❌ 变更失败，已自动回滚到执行前的状态。
   失败步骤：新增 1 条入站规则
     原因：platform: 创建防火墙规则失败（需要以管理员身份运行）:
           New-NetFirewallRule : Access is denied.
```

#### 一处语义调整

空计划（规则已存在）原先不写日志记录，理由是不产生噪音。现在它**会写**：
记录的价值不只是"改了什么"，还包括"用户在那个时刻想做什么"。事后排查
"我明明点过开放端口，怎么还是不通"时，这条记录能立刻排除掉一半可能；
而且接口层需要一个可返回的东西。



### M3-e 引导式外部验证

**它解决的问题**：本机的一切检测通过之后，还剩最后一个问题 ——
从外面到底能不能连上。本机回答不了：从本机访问自己的公网地址走的是
回环或直连，无论运营商是否放行都会"成功"。

唯一的办法是让一台**真正在外面的设备**去访问一次，而用户手边就有：
他的手机（关掉 Wi-Fi，走 4G/5G）。

#### 判断依据只有一处：来源地址

| 来源 | 结论 | 说明 |
|---|---|---|
| 公网地址 | `reachable` | 链路确实通 |
| 本机/内网地址 | `hairpin_only` | **什么也证明不了** |
| 一直没访问 | `unreachable` | 结合本机检测全绿，指向上游封禁 |

`hairpin_only` 单独成一档而不是并进失败，是这里最关键的设计：它既不是
成功（会让用户以为配好了），也不该被当成失败（用户只是还没拿手机试）。

#### 真机上抓到的假阳性

首次跑通链路时，测试断言"本机访问应当被判为回环"，结果失败 ——
页面显示的是**"链路是通的"**，而来源地址是 `2409:8a50:6a1:7450::50b`，
也就是**这台机器自己的公网 IPv6**。

原因：**IPv6 没有 NAT**。从本机访问自己的公网地址时，连接是直连的，
来源地址就是那个**全局单播地址** —— 光按地址类型分类，它完全正常。

这个假阳性在真实产品里的表现是：用户"在自己电脑上试一下"，看到
"验证成功"，于是放心地去配其它东西；等他真的用手机访问时才发现
根本连不上，而那时他已经不记得哪一步是对的。

修法：新增 `SourceSelf` 分类，把来源地址与**本机拥有的全部地址**比对。
枚举每次现做而不是缓存 —— 运营商前缀一晚上能变好几次，而缓存恰好会在
用户最可能测试的时候给出错误判断。

CLI）。用 `==` 比较的话，任何一层包装都会让它静默失效，于是"服务已经装过了"
变成一句红色的失败，而用户会去手工卸载一个本来就装好的服务。

**二、`runtimeinfo.processAlive`**

它的返回值直接决定 `Connect` 是否认为内核还活着，两个错误方向都有代价：

```

真内核 + 判定"已死"           → 客户端说"内核没在运行"，用户又启动一个
```

在 Windows 上**恒返回成功**（它不做任何系统调用）。

其中一条是**元测试**（`TestProcessAliveIsNotConstant`）：要求"自己活着"与
"pid=0 不存在"给出**不同**的答案 —— 一个恒定实现无法同时满足，而它正是
最糟的那种"通过"。

`convertRule` 那条尤其要紧 —— 探测阶段会把系统里所有规则都读回来，而
"协议是 Any / 端口是 Any / 端口是个列表"的规则都必须被跳过，否则回滚时
会删掉别人的规则。补了 9 个"必须跳过"的用例与 4 个"必须认领"的用例
（后者防止"全都拒绝"式的假通过）。

`extractCLIXMLErrors` 的测试则用了**真机上发现的折行形态**：长错误会被
PowerShell 折成多个 `<S>` 节点，于是"逐个过滤噪声"会把续行片段
（`tFirewallRule], CimException`）留下来。实现因此是"按位置截断"——
遇到第一条定位信息就停下。测试把那个行为钉住，并断言结果里不含
`CategoryInfo` / `FullyQualifiedErrorId` / `At line:` / `CimException`。

##### 还剩 50 个，分布是明确的

主要是非 Windows 的实现（`firewall_darwin.go` / `firewall_linux.go` /
`service_*.go` / `paths_*.go` / `secret_unix.go`）—— 它们本机跑不到，
只能靠 CI 的三个平台矩阵。以及 `ddnsgo/socket_bind_*.go`（移植代码）。

这 50 个不是"忘了测"，而是"**在这台机器上测不了**"。区别很重要：前者是
疏漏，后者是跨平台项目的固有约束 —— 而约束必须被**写下来**，否则它会
静默地变成"我以为测过了"。
##### 同一类缺口的第二处：密钥库从未被测过

沿着"平台标签挡住、可能从未被测过"这条线索继续查，找到了**更严重的一处**。

`internal/secret/manager_test.go` 里有一句注释：

> 刻意不做替身：主密钥的生成与持久化正是这一层要验证的东西……
> **各平台的后端差异由 internal/platform 自己的测试覆盖。**

**而那些测试此前并不存在。** `internal/platform` 里针对三个密钥存储实现
（`secret_file.go` / `secret_unix.go` / `secret_windows.go`）的测试是**零**。

这一层保护的是**主密钥**：主密钥丢了，所有已加密的凭据永久无法解密。

补了 20 条：

**`secret_file.go`（跨平台兜底，本机可测）**

| 测试 | 抓什么 |
|---|---|
| 往返 | 基本读写 |
| **二进制值** | 32 字节真随机值很可能含 NUL 与非法 UTF-8；任何"当字符串处理"的环节都会损坏它，而症状是"凭据突然全部解不开"且无线索。真随机值里出现 0x00 的概率约 12% |
| 权限 0600 / 0700 | 没有系统密钥库时，**权限就是全部的保护** |

| 反复覆盖 + 无临时文件 | 中途失败留下截断的密钥文件 = 主密钥丢失 |
| 删除幂等 | 卸载/重装脚本会重复调用 |
| **名称拒绝路径穿越** | 13 个恶意名 + 7 个合法名（后者防止"全都拒绝"式的假通过） |

| Get 不创建目录 | 一次纯粹的"读一下"不该有副作用 |

**`secret_windows.go`（DPAPI，本机可测）**

其中最重要的一条是 **`TestDPAPIPlaintextNeverTouchesDisk`**：它不看接口的
返回值，而是**直接去读磁盘上的字节**，断言里面没有明文主密钥、也没有明文
片段。

理由是：如果实现不小心把明文也写进了文件，**从外部看不出任何区别** ——
功能一切正常、读写都对。加密就成了一件装饰品，而没有任何测试会失败。

##### 一处我自己写错的测试

权限断言最初用了 `os.Getenv("GOOS") == "windows"` 作为跳过条件。而 `GOOS`
**不是运行期环境变量**（那是 `runtime.GOOS`），于是那个条件永远不成立 ——
测试在 Windows 上必然失败。改成 `runtime.GOOS` 之后正常跳过。

这类错误的形状值得记下来：**跳过条件写错会让测试在错误的平台上运行**，
而它的表现是"红"，所以还算容易被发现。反过来（本该跳过却没跳过、
或者本该运行却被跳过）就会变成一条永远绿灯的空测试。
##### 核实目标里的「命名管道/UDS」：UDS 从未被测过

目标那一条写的是「命名管道/**UDS** + token」。命名管道在 Windows 上我反复
验证过，于是这一轮去核实 UDS —— 发现：

**`listenLocal` / `dialLocal` 没有任何测试真正跑过它们。** `endpoint_test.go`
只测了 `unix://` 这种地址串的**解析**，而解析对了不等于套接字能建起来、
能连上、能在退出时被清理。

而 UDS 是 Linux / macOS 上**唯一的**本地管理通道（D08）：它坏了，那些平台上的
CLI 与验证控制台都连不上内核。

实现本身看起来是对的（残留套接字清理、0600 权限、Close 时删除文件），但
"看起来对"不是验证。补了 8 条测试：

| 测试 | 抓什么 |
|---|---|
| 往返 | 建、连、收发、关 |
| 权限 0600 | **权限就是这条通道的访问控制** |
| 关闭即删除文件 | "内核已退出"应当在文件系统上可见 |
| 残留套接字可回收 | 崩溃后 bind 不再 EADDRINUSE |
| **拒绝覆盖普通文件** | 同名普通文件是用户的数据，不能被无声删掉 |
| 拒绝错误的方案 | 类 Unix 上给命名管道地址要明确报错 |
| 默认路径在运行目录下 | 套接字落点 |
| 并发连接 | 内核同时服务 CLI / 控制台 / GUI，多连接是常态 |

##### 本机跑不了 —— 但这条路是通的

这些测试带 `!windows` 构建标签，因此**在 Windows 开发机上不会执行**。
能做的三件事都做了：

1. **交叉编译验证**：`go vet` 与 `go test -c` 在 linux/amd64、darwin/arm64、
   freebsd/amd64 上全部通过（生成了 8.5 MB 的 Linux 测试二进制）；
2. **确认 CI 会跑它**：`.github/workflows/ci.yml` 的 test job 矩阵是
   `[ubuntu-latest, windows-latest, macos-latest]`，跑 `go test ./...` ——
   UDS 测试会在 Ubuntu 与 macOS 上真正执行；
3. 把"本机跑不了"这件事**写进了测试文件的注释**，而不是让后来的人以为
   它跑过了。

这是本项目里第一块"只能靠 CI 验证"的代码。它的存在本身说明了一件事：
**跨平台项目里"我没法在这台机器上测"是一个必须显式记录的状态**，
否则它会静默地变成"我以为测过了"。
##### 尝试控制台本地化：朴素做法在这里行不通

动手前先写了个工具自动抽取 `index.html` 的文案（生成 `data-i18n` 属性 +
消息表）。抽出了 128 条 —— 然后发现**大半是不可翻译的碎片**：

console.t028 = 所有
console.t029 = AAAA 记录都要重写，而不是只改一个地址。

原文是一句话，被 `<strong>` / `<code>` 切成了四段：

```html

<code>/64</code> 前缀，该前缀下的<strong>所有</strong> AAAA 记录都要重写，

逐文本节点替换在这里**做不到正确的结果** —— 翻出来的英文会语序错乱，

**文件已还原**，没有留下半成品。正确的做法是一个**设计决定**，不是脚本

代价是消息表里存 HTML 片段 —— 对自有的内嵌资源可以接受，但要写明。

##### 一个需要区分的概念：日志不是文案

统计剩下的小包时发现 `internal/event` / `internal/console` / `internal/audit`

##### 方法上的一个改进：字面量级替换

前几轮用的是"整块源码替换"（把 `Short:` / `Long:` 连同下一行一起换掉）。
它对单个字符串很好用，但对**跨多行的块**很脆 —— 缩进只要差一个空格就
匹配不上。这一轮 `verify.go` 一次就漏了 16 处，全部是因为我**凭印象写的
缩进**与源码不符。

改成**字面量级替换**（只替换 `"…"` 那一段本身）之后，同样的工作一次
全中。理由是这些字符串在源码里都是**独立的参数**，替换字面量就已经足够，
而不必把它所在的整块结构也复述一遍。

由此得到一条更一般的做法：**替换的粒度越接近"要改的那一点点"，越不容易
因为周围的格式而失手。**

##### `go vet` 抓到了三处真实风险

Go 1.24+ 的 `printf` 检查会拦下"格式串不是常量"的调用：

```
doctor.go:119: non-constant format string in call to fmt.Fprintf
```

那些调用**没有可变参数**（`fmt.Fprintf(w, i18n.T("…"))`），因此一旦译文里
出现 `%`，就会打出一句 `%!x(MISSING)` 之类的乱码。改成 `fmt.Fprint` 即可。

更要紧的是 **cobra 处理 `--help` 发生在 `PersistentPreRunE` 之前**，
所以把语言解析放在 init 里，对帮助文本**永远来不及**。

真机症状（帮助正文恰恰是用户最先看到的东西）：

```
$ isc --lang en credential add --help
                                        ← 子命令输出已经是英文

我只验证了 `RunE` 的输出，没有验证帮助文本。**"转换完成"这个结论下得
太早了。**

修法是把语言解析**提前到构造命令树之前**（`App.resolveLangEarly`，
在 `Execute()` 里、`New()` 之前调用）。它自己扫 `os.Args` 找
`--lang` 与 `--data-dir` —— 后者决定运行时文件在哪，而"内核设置"要从
那里读。

代价是多了一份**独立于 cobra 的参数解析**（`flagValue`）。两份解析必须
对同一种写法给出一致的答案，否则会出现"`--lang en` 能用、`--lang=en`
却不生效"这种极难归因的问题。为此加了 11 条表驱动测试，覆盖空格/等号
两种写法、混在其它参数里、前缀误匹配等。

##### 顺带抓到一个真缺陷：改语言要重启内核才生效

追查"为什么 `--lang en` 时字段说明还是中文"的过程中发现：**英文译文其实
早就有了**（`provider.field.api_token` = `"API token"`）。真正的问题是
`i18n.SetDefault` 只在**两处**被调用：

```
cli/root.go:147        每次 CLI 运行都应用
daemon/daemon.go:233   只在**启动时**应用一次
```

于是运行期改语言会出现两端不一致：命令行立刻变了，而**服务端生成的内容
仍是启动时那个语言** —— 例如 `/v1/providers` 里的凭据字段标签与说明。
用户唯一的办法是重启内核，而界面上的"语言"开关看起来是即时生效的。

修法是给 `settings.Service` 加一个 `SetOnChange` 回调点，由守护进程接上
`i18n.SetDefault`。回调**同步**调用，且放在**落库与生效之后、返回之前**：

- 放在落库之前 → 一次失败的保存会留下已经生效的副作用
- 异步调用 → "改完设置立刻发一个请求"会看到旧值，而那正是用户会做的事

真机验证（不重启内核）：

```

改后  --field token=<API token> ... Create it under My Profile → API Tokens in the
                                     Cloudflare dashboard…
```

##### 语言优先级已闭合：--lang > 内核设置 > 默认值

上一轮把"CLI 只认 `--lang`、不跟随内核设置"记为未完成。这一轮做掉了，
顺带解决了随之而来的**混排**问题。

`--lang` 原本只能改 CLI 自己进程的语言，而字段说明是**服务端**渲染好
发过来的 —— 于是 `isc --lang zh-CN credential fields cloudflare` 会打出：

```
--field token=<API token>  （必填） [敏感]  Create it under My Profile…
                 ↑ CLI 串是中文        ↑ 服务端串是英文
```

修法分三层：

- `i18n/context.go`：`WithCatalog` / `FromContext` / `FromHeader`。
  **用 context 而不是改全局** —— 接口是并发的，两个客户端可以同时用
  不同语言请求；把请求语言写进全局变量会让它们互相覆盖，而那种缺陷
  只在并发时出现，是最难复现的一类。
- `api`：一个 `Language` 中间件按 `Accept-Language`（或 `?lang=`）为
  每个请求选定目录。认标准头而不是自定义头：**浏览器会自动带上它**，
  因此控制台不用写任何代码就能跟随浏览器语言。
- `cli`：`App.connect` 把**显式指定**的语言带上。只有显式指定时才带 ——
  没指定时应当跟随内核设置，而"把默认值也发过去"会让内核设置永远不生效。

顺带消掉一处重复：`Connect(ctx, app.paths.RuntimeFile())` 此前在 **31 处**
被逐字重复，而语言需要跟着每一次连接走。做成 `App.connect` 之后，
漏掉任何一处都会产生的"这条命令语言不对"这类问题从根上没了。

真机验证四种组合，**没有一种会混排**：

| 内核语言 | CLI `--lang` | 结果 |
|---|---|---|
| zh-CN | `en` | 全英文 ✓ |
| zh-CN | 无 | 全中文 ✓ |
| en | `zh-CN` | 全中文 ✓ |
| en | 无 | 全英文 ✓ |

加 6 条测试，其中一条专门钉住**隔离**：context 里的目录不得污染全局。

##### 顺带修掉一个由偶发测试暴露的真竞态

全量测试时 `TestCancelFinishedJobRejected` 挂了一次，单独跑却稳定通过。

追下去发现不是测试问题：任务的收尾顺序是「任务体返回前先把状态落库，
之后才轮到 `run` 的 defer 把它从在途表 `e.cancels` 里摘掉」——中间还夹着
日志与事件发布。于是存在一道真实的缝隙：**状态已是终态，但在途表里还有它**。
只看在途表的 `Cancel` 会得出"可以取消"的结论，然后取消一个早就做完的
任务，并向客户端**报告成功**。

客户端会以为它取消掉了一件事，而那件事其实已经完成、并且可能已经产生了
副作用。窗口很小，但语义是错的。

回归测试**不去赌那道缝**（靠时序去撞的测试会在最需要它的时候变得不稳定），
而是直接构造它的前提：手工把终态记录塞进存储、同时在在途表里留一个条目。
并验证过它确实能抓到 —— 撤掉修复后它立刻失败，报「得到 `<nil>`」。

M3 验收第 3 条要求「故意封掉端口后，isc doctor 能明确指出是运营商侧封禁
而非本机问题」。链路闭合的方式是：`isc verify` 收到过零次公网访问，就是
上游挡住的证据 —— 把它的结论回喂给可达性检查。

- **`hairpin_only` 不产生结论。** 只收到回环访问说明不了上游通不通（用户
  可能只是用 WiFi 而不是 4G 打开的）。把它当成「被封了」是一个**错误的
  诊断** —— 而错误的诊断比没有诊断更糟：它会引导用户去联系运营商，而真正
  的问题是他自己的验证方式不对。
- **结论有 24 小时有效期。** 用户今天验出「被运营商封了」，下周换了宽带之后
  那个结论就不再成立。留着它会让 doctor 给出基于上周情况的错误结论。
- **结论与会话分开存。** 会话是短命的（默认十分钟），而结论应当比会话活得
  久 —— 验过一次之后再跑 doctor 应当还能看到它，而不是回到「未知」。

##### 「不支持校验」与「校验失败」必须分开

阿里云 / 腾讯云 / 华为云 / GoDaddy 没有只读的校验端点，而用「列一次域名」
来冒充会要求额外的权限 —— 那会把只有 DNS 编辑权限的**最小权限账号**误判为
无效。因此 `dns.Verify` 返回一个可区分的 `ErrVerifyUnsupported`，而接口对它
的响应是「该服务商不支持校验」，不是「凭据不可用」。两者的下一步完全不同。

```

### 对照既定验收标准的逐条审计

这一轮做的是**把 M0–M5 每一阶段写下的硬验收标准逐条对照实际情况**，
而不是接着往下写功能。它抓到两个从代码里看不出来的缺口。

#### 缺口一：`cert.renewed` 定义了却从未被发出

M4 验收第 3 条写的是"证书到期前自动续期并推送 `cert.renewed` 事件"。

而 `internal/acme/manager.go` 里只有：

```go
m.publish(event.TypeCertFailed, name, req.Domains, err)
m.publish(event.TypeCertIssued, name, req.Domains, nil)
```

`event.TypeCertRenewed` 这个常量**存在、名字也对**，但没有任何地方发出它。
于是配了"只收续期通知"的用户什么都不会收到 —— 而这条缺口从代码里
完全看不出来（常量在、事件类型在、管理器的 publish 调用看起来也齐全）。

修法是记录"这次之前是否已有证书"，首次签发与续期发不同的事件。
其中一处判断值得说明：**读取现有证书失败时也算"已有证书"** ——
文件在那里，只是读不出来；当成首次签发会让用户收到"证书已签发"，
而他期待的是"续期失败"的告警。

#### 缺口二：M3 验收点名的 `isc init` 不存在

M3 验收第 1 条："一台全新机器，从 `isc init` 到「手机 4G/5G 打开测试页」
全流程可走通。"

而 `isc` 的全部子命令里没有 `init`。这条验收此前无法成立。

新增的 `isc init` 是一个**引导而不是向导**：它探测环境（公网 IPv6、
委派前缀、防火墙能力、低端口权限），然后打印一份**填好了真实值**的
下一步清单。理由是这个产品的使用者多半已经知道自已想干什么，而一个
交互式向导会把他已经知道的事情再问一遍。

它**只读**，不修改任何系统状态 —— 一个会改系统的引导命令会让用户
不敢运行它。

真机输出（本机是中国移动家宽，无公网 IPv4）：

```
【环境】
  ✅ 公网 IPv6：2409:8a50:6a1:7450::50b, ...
     网卡：WLAN
  ℹ️  委派前缀：2409:8a50:6a1:7450::/64
  ℹ️  没有公网 IPv4 —— 这在国内家宽上是常态，不影响使用
  ✅ 防火墙后端可用（放行端口时需要管理员权限）
  ✅ 可以绑定低端口（443 等）—— windows-native
```

#### 一处刻意的判断：CGNAT 不算公网 IPv4

国内家宽最常见的说法是"运营商给了公网 IP"，而实际拿到的地址常常落在
`100.64.0.0/10`（RFC 6598，运营商级 NAT）里。那段地址**不能**用来对外
提供服务 —— 它是运营商内部的一层 NAT。

不排除它会让 `isc init` 给出"你有公网 IPv4"的结论，而用户据此去配 A 记录，
然后在外面怎么都访问不通。有专门的测试钉住这个段的两个边界
（`100.63.255.255` 与 `100.128.0.0` 是公网，`100.64.0.0` 与
`100.127.255.255` 不是）。
### M3-d 端口层诊断

在用户开一条防火墙规则之前，先看两件事：**那个端口上有没有东西在听**、
**本机有没有权限绑它**。只做"开端口"而不做这两项检查，会产生两种最难
排查的失败：

```
端口上没有服务
  防火墙规则开好了，用户从外面访问却什么都不通。他会去查路由器、
  查运营商、查 DNS —— 而真正的原因是本机上根本没有服务在监听。

没有权限绑低端口
  用户在反代里配了 443、界面上显示"已启用"，而后台每次启动都失败。
  他会以为是自己配置错了，而不是权限不够。
```

#### 为什么用"连一下"而不是读 /proc/net/tcp

读内核连接表看起来更"干净"，但各平台的文件位置与格式完全不同
（`/proc`、`sysctl`、`GetExtendedTcpTable`），要写三份实现；而且它回答的是
"内核里有没有这条记录"，**而不是"客户端能不能连上"** —— 后者才是用户关心的。

连一下是所有平台通用的，而且它测的正是真实路径。代价是它有副作用
（会在服务端留下一条连接记录），因此只在用户**主动点检查或生成计划**时发生，
而不是定时轮询。这一点写进了代码注释。

#### 两项的严重程度刻意不同

| 检查 | 状态 | 为什么 |
|---|---|---|
| 端口上没有服务 | **警告** | 用户可能正要启动它。"先开规则、再起服务"在"先把网络配好再部署服务"的流程里很自然，做成失败会拦住一个合理的顺序 |
| 没有权限绑低端口 | **失败** | 没有权限就一定绑不上，重试、等一会儿、改配置都不会让它变好 —— 让用户先应用再看它失败只是浪费一次系统变更 |

失败项直接拒绝生成计划，警告项进入 `change.Plan.Warnings`。

#### 真机上抓到一处文案缺陷

两条文案各自都通顺，拼接之后是：

> 端口 18099 上没有服务在监听 开放这个端口之前，先确认本机有服务在监听 18099 —— …

事实句不以标点结尾、提示句又是完整句子，拼起来成了重复又拗口的连体句；
而且提示里把 Detail 刚说过的事又说了一遍。

修法是 `joinCheckText`：需要时补句号，并让提示只说**后果与下一步**。
加了测试守住它（含"已经有标点时不重复添加"这类边界）。

#### 低端口边界

1023 是特权端口，1024 不是。这个边界很容易写成 `<=1024` 或 `<1000`，
而错了之后用户会在 1024 上收到一条无意义的警告 —— 而噪音会让用户忽略
真正重要的那几条。有专门的测试钉住它。

#### 验证

- 真机：无服务监听的端口 → 计划带警告；有服务监听（真起了一个
  TcpListener）→ 无警告；UDP → 如实报告"无法探测"。
- 21 条单元测试（含 IPv6-only 监听、并发安全、上下文取消）。
### M3-c2 Linux nftables 与 macOS pf 后端

三平台防火墙后端至此齐全。**但要说清楚验证情况**：

| | 实现 | 验证 |
|---|---|---|
| Windows | PowerShell NetSecurity | ✅ 真机（非管理员路径已验证；创建规则需管理员） |
| Linux | nftables + `inet isc` 独立表 | ⚠️ 编译 + 纯逻辑测试；**无真机** |
| macOS | pf + `/etc/pf.anchors/isc` | ⚠️ 同上；**无真机** |

#### 两个后端的模型根本不同

这个差异决定了后端怎么写：

```
nftables   增量。每条规则是一个对象，有内核分配的 handle，可以单独增删。
pf         声明式。配置是一整份文本，pfctl 读进去之后整体替换。
           规则没有身份，也没有 handle。
```

因此 pf 这边**没有"差集"这回事**：期望状态直接渲染成 anchor 全文，写进去、
重载。代价是任何一次改动都会重载**全部**规则，而重载有可见的代价 ——
所以 pf 后端会先比较文件内容，**没变就不重载**。

而 nftables 那边刻意把**新增排在删除之前**（与直觉相反）：先删后加会让防火墙
出现一个短暂的空窗，那些端口在两条命令之间是关闭的，对正在使用的连接来说是
一次可观测的断开。先加后删的代价只是极短一瞬间可能同时存在新旧两条规则 ——
那只会让某个端口多放行几毫秒，而不是把它关掉。

#### 纯逻辑与平台调用分开——又一次证明是对的

与 systemd / launchd 同样的做法：命令拼装、ruleset 解析、anchor 渲染、
注入校验放在**没有构建标签**的文件里，只有"执行 nft / pfctl"是平台相关的。

测试覆盖了那部分，而它是风险最集中的地方：命令拼装错了 nft 会报语法错误、
JSON 解析取错一层就解析不到、换行符能越出配置行变成一条额外指令。

**这个做法当场抓到两处真 bug**：

`ruleNames` 与 `newChangeID` 定义在 `firewall_windows.go` 里，而那个文件带
`//go:build windows` —— 于是它们**只在 Windows 上存在**。写 Linux 后端时
才发现拿不到。

同类问题紧接着又出现一次：`renderNftDiff` 定义在 `firewall_linux.go` 里，
写 macOS 后端时编译失败。

这类问题的表现很隐蔽：在开发机（Windows）上编译一切正常，而 CI 的 Linux
构建才会失败。修法是把共用逻辑放进 `firewall_common.go`，并明确"共用逻辑
必须有明确的落点，而不是碰巧和某个后端写在一起"。

#### 几处刻意的设计

- **用独立的表 / anchor，不碰用户的配置**。nftables 用 `inet isc` 表，
  pf 用 `/etc/pf.anchors/isc`。卸载时整表删掉、或删掉 anchor 引入行即可，
  不会与用户自己的规则混在一起。`AppendPfAnchor` **只追加**，从不重写
  `/etc/pf.conf` —— 那里面可能有别人的配置。
- **改 `/etc/pf.conf` 前先备份**。改坏了会让整个防火墙失效，而那时用户可能
  连 SSH 都进不去（pf 管的就是入站连接）。备份失败不阻断，但会打印提示。
- **先 `pfctl -n` 校验语法再加载**。一份语法错误的配置会让 `pfctl -f` 失败，
  更糟的是**把已经在生效的规则全部清掉**。`-n` 只解析不加载，
  把问题挡在造成影响之前。
- **解析器容忍未知结构**。ruleset 里大部分规则不属于 ISC，形式五花八门；
  解析器遇到不认识的结构必须**跳过而不是报错** —— 报错会让整个 Inspect
  失败，而用户会看到"无法读取防火墙状态"，完全不知道问题出在别人的规则上。
- **回滚是"重新计算"而不是"反向执行"**。中间可能有人手工改过规则、或者内核
  重启过；重新计算对任何中间状态都成立，而反向执行只对"什么都没变"成立。

#### 一处如实记录的降级

pf 的 `Rollback` **恢复不出来源限制**。规则名编码了协议与端口，而来源地址
没有（它不在名字里）。

实际影响很小 —— IPv6 直连场景下通常不限制来源 —— 但如果用户当初配了来源
限制，撤销之后的规则会变成"任意来源"。这是一个已知的降级，而不是一个
被忽略的问题。
### M3-c Windows 防火墙后端

**不用 `netsh`，用 PowerShell。** `netsh advfirewall firewall show rule`
的输出是给人看的**本地化文本**：中文 Windows 上是"规则名称""已启用"，
英文系统上是 "Rule Name" / "Enabled"。解析它意味着对每种系统语言各写
一套解析器，而漏掉一种语言的症状是"规则没读到、于是重复创建了一堆"。
PowerShell 的 NetSecurity 模块返回结构化对象，字段名与语言无关。

**脚本用 `-EncodedCommand` 传入**（UTF-16LE + base64），因此不存在任何
命令行引号转义问题 —— 那正是把参数拼进命令行最容易出错的地方。这段脚本
会以**管理员身份**执行，一次注入就能拿到整台机器的控制权。

**写入脚本前做二次校验。** `ruleNamePattern` 只允许 `[a-z0-9-]` 与合法
端口，任何不合规的名字被整条跳过而不是原样拼进脚本。这一层校验是
**冗余的**（调用方已经校验过），但"以为上游校验过所以这里不用管"
正是注入漏洞的经典成因。

#### 写测试时抓到的三个缺陷

1. **`parseRuleName` 的捕获组索引写错了**（用了 `m[2]`/`m[3]`，
   实际只有两个组）。任何一条真实的规则名都会让它索引越界 panic，
   而它被 `createScript` 调用 —— 那是"开放端口"的必经之路。
   **这条路径在写测试之前从未被跑到过。**
2. **`validRuleName` 与 `parseRuleName` 判断不一致**：前者只跑正则，
   于是 `isc-x-tcp-99999`（端口超出 uint16）被判为合法，而后者拒绝它。
   结果是同一个名字"能删不能建"。修法：`validRuleName` 直接复用
   `parseRuleName`，两者永远不会再分叉。
3. **规则名允许前导零**，于是 `isc-x-tcp-70` 与 `isc-x-tcp-070` 指向
   同一个端口，破坏了"规则名即身份"的假设。

#### 补上了上一轮留下的缺口

上一轮报告的限制是"跨进程撤销做不了，只能让用户手动清理"。那个结论
**是错的** —— 它把框架的设计缺口转嫁给了用户。

根因是 `change.Record` 里只有渲染后的人类可读差异，没有后端重建撤销
动作所需的原始数据。补上 `Plan.Payload` / `Record.Payload`
（migration 0004）之后，撤销一条防火墙规则所需的信息（当初创建了哪几条）
被原样持久化，**跨越内核重启依然可用**。

`Revert` 仍然有两条路径会明确报错而不是假装成功：记录来自更早的内核
版本（没有 payload）、或当前平台后端不可用（数据目录被搬到另一台机器）。
两种情况下都给出规则名前缀，用户据此能在系统防火墙里找到它们。

### M3 已发现的真实缺陷

**Teredo 隧道地址被当成了可用于公网访问的 IPv6。**

`isc doctor` 的首次真机运行报告：

```
✅ 全局 IPv6 地址
     在 WLAN、Teredo Tunneling Pseudo-Interface 上找到 4 个可用于公网访问的 IPv6 地址
```

`netip` 的 `IsGlobalUnicast()` 对 `2001:0::/32` 返回 true —— 它确实落在
`2000::/3` 里。但 Teredo 与 6to4 都是**隧道**地址，只能用于出站穿透，
不接受入站连接。把伪接口报出来的 4 个地址当成可用地址，会把用户引向
一条走不通的路，而他会在路由器上白白折腾很久。

修法：`IsGlobalIPv6` 排除 Teredo（`2001:0::/32`）、6to4（`2002::/16`）、
文档网段（`2001:db8::/32`）与 ORCHIDv2（`2001:20::/28`）；
另把 `teredo` / `isatap` / `6to4` 加入虚拟网卡名称表。

修复后真机输出：`在 WLAN 上找到 3 个可用于公网访问的 IPv6 地址`、
`检测到 1 个委派前缀`。

> 这类缺陷只有跑在真实机器上才会暴露 —— 单元测试的构造数据里
> 不会出现 Teredo 伪接口。

### M4-c2 通知通道的配置

#### 不再定义第二份配置结构体

早先存储层会有一份与 `notify.ChannelConfig` 逐字段重复的类型 —— 而那是
**一处必然出错的重复**：给一边加字段、忘了另一边时，接口返回 200 而值
根本没存进去。

这个项目里已经栽过两次（代理设置、ACME 设置），因此这次直接用类型别名，
并加了编译期接口断言 `var _ notify.ChannelStore = (*NotifyChannels)(nil)`。

#### 真机抓到一个会误导用户的缺陷

测试通知显示 ✅ 成功，但那个 Webhook 指向的端口**根本没有服务在监听**。

原因：通道配了 `min_severity: warning`，而测试消息是 `info` —— 被级别
过滤器挡掉了，而过滤器把"被过滤"报成 `nil`（刻意让它不算失败，理由是
那会在投递记录里留下一堆假失败）。

但**测试通知是个例外**：用户点"测试"时的意图是"现在真的发一条"，
级别过滤在这里不该生效 —— 想看通道是否配通，就必须真的打一次目标地址。

修法是 `SendNow` 剥掉通道外面的全部包装（`dynamicMarker` 与
`levelFilter`），直接打到真正的通道上。**剥包装用循环而不是一次断言** ——
只剥一层会让这个保证在某些组合下**静默失效**（仍然报成功），而静默失效
正是要避免的。

修复后真机验证：Webhook 被真正联系（10 秒后超时，证明发出了真实请求），
而不是之前的瞬间假成功。

#### 其它几处设计

- **保存前逐个构造一遍**：模板语法错误之类的"构造期才暴露"的问题在保存时
  就被挡住，而不是等到某天真的要发通知时才发现。
- **加载配置失败的通道被跳过并记录**，而不是让整个加载失败：一条通道配错
  了不该让其它通道也失效。
- **启动时先加载通道再订阅事件**：顺序反了的话，启动瞬间的事件会在通道
  加载完成之前到达，而那些通知会被静默丢掉。
- **每通道独立级别阈值**：级别过滤做成包装而不是放进 Manager，于是
  "错误发到手机，全部发到日志"这种常见需求可以表达。



### M4-c 通知中心

#### 核心问题不是"能发出去"，而是"不被刷屏"

内核产生的很多事件会**成串出现**：

```
IPv6 前缀抖动      重拨一次产生若干条地址变化事件
服务商限流         连续几次更新失败
证书续期失败       定时重试，每小时一次
```

原样转发的话，用户会在几分钟内收到十几条一模一样的消息，**然后关掉通知** ——
而那之后真正重要的那条他也看不到了。

因此三件事是核心：

**去重键**。键里只放"这件事是什么"（任务 ID、证书名），**不放会变的
部分**（IP 地址、错误文本）。放了后者的话地址一变就是一条新消息，
去重完全失效 —— 而事件风暴正是它要挡的东西。

**静默期**（默认 5 分钟）。足够长到把一次事件风暴收进一条通知，
又足够短到让持续存在的问题在一刻钟内被再次提醒。

**汇总补发**。这是最容易漏掉的一环：静默期内被抑制的消息只计数
是**不够的** —— 用户会以为那段时间什么都没发生，而实际上是他最
关心的那类事件在反复出现。静默期过后会补发一条"另有 N 次同类事件"。

#### 其它几处刻意的设计

- **`Notify` 非阻塞，队列满时丢掉最旧的**。通知是旁路功能，它绝不能
  拖慢动态解析或证书续期这些主线任务。丢最旧而不是最新：积压时用户更
  需要知道刚刚发生了什么。
- **单个通道失败不阻断其余的**：一个 Webhook 配错了不该让邮件也收不到。
- **投递结果被保留**。"我的通知到底发出去了没有"是用户配置通道时问得
  最多的一个问题，而只写日志的话他得去翻日志文件。
- **Webhook 只允许 http/https**：`file://` 之类的 scheme 会让这个功能
  变成一个"能读写本机任意文件"的入口。
- **模板语法错误在保存配置时就报错**，而不是等到发送时。放到发送时才发现
  的话，用户会看到"通知发不出去"，而真正的问题是模板里少了一个括号。
- **日志通道始终登记且永不失败**：用户还没配外部通道时，通知至少会出现在
  日志与事件流里，而不是无声无息地消失。

#### 哪些事件值得通知

原则是"**用户需要采取行动或需要知道**"，而不是"发生了什么"。全都要通知
的话，用户会在一天之内关掉它。

| 通知 | 不通知 |
|---|---|
| 解析失败、地址已更新 | 每次解析成功（无变化） |
| 证书签发 / 失败 | 作业进度 |
| 变更失败（回滚失败时提级） | 日志写入 |
| 被中断的变更 | |

回滚失败被**单独提级**：它意味着系统既不是原状、也不是目标状态，
必须比普通的"变更失败"更醒目。



### M4-b3 把 ACME 接到守护进程上

#### 又一次"加了字段却没接线"——这次从根上修

给 `settings.Settings` 与 `settings.Patch` 都加了 ACME 字段，却**忘了给
接口层那个匿名解码结构体加** —— JSON 里的未知字段被静默忽略，接口返回 200
而值根本没变。

这是**同一类错误第二次出现**（上一轮是代理字段）。因此这次不从根上修的话
还会再犯：让 `UpdateSettings` **直接解码进 `settings.Patch`**，取消那份
逐字段重复的匿名结构体。

复用一个结构体就从根本上消除了这类疏漏 —— 没有第二份需要同步的字段列表，
也就没有"忘了同步"这回事。

#### 真机上抓到的另一个缺陷：切换 HTTPS 没有效果

`applyProxySettings` 只比较**端口**，于是用户在已经运行的代理上打开 HTTPS
开关时"什么都没发生" —— 代理还在用明文跑，而界面上开关明明是打开的。

修法：`proxy.Status` 增加 `TLS` 字段，端口或 TLS 模式任一变化都重启监听。

真机验证：

```
反向代理已启动 port=18443 routes=0                    （明文）
反向代理已停止 port=18443                              （切换时先停）
反向代理已启动（HTTPS） port=18443 min_version="TLS 1.2"
```

#### 设置校验

`proxy_tls` 为真而没配 DNS-01 凭据时**直接拒绝保存**，而不是等签发失败。
后者的症状是"浏览器报证书错误"，而用户完全不知道是设置少填了一项。



### M4-b2 证书续期管理与 TLS 集成

#### 续期判断为什么不能只看时间

用户给一条 HTTPS 路由**加一个域名**之后，现有证书不覆盖新域名 ——
而**这与剩余有效期无关**，证书可能刚签了三天。只按时间判断的话，
新增的域名要等三个月才会生效，而用户完全不知道要等。

因此判断分两步：先看域名覆盖，再看有效期。

有效期用三分之一规则（对 Let's Encrypt 的 90 天证书就是提前 30 天），
并加了两条边界：

- **下限 3 天**：有些 CA 签发 7 天的证书，按三分之一算只有 2.3 天，
  一次失败加上周末就可能过期。
- **上限为寿命的一半**：否则短期证书会陷入"刚签完就要续"的循环。

#### 三个真机上/测试中抓到的缺陷

1. **零值签发时间导致"永远不续期"。** 判断寿命时代码只挡了
   `lifetime <= 0`，而零值时间的 Unix 时间是 1 年 1 月，于是
   `ExpiresAt.Sub(IssuedAt)` 得到一个**约 97 年**的寿命，阈值随之
   变成一个永远达不到的数。表现是证书一直不续期，直到过期。
   修法：显式检查 `IssuedAt.IsZero()`。

2. **`Store.Load` 对无法解析的证书静默返回零值。** 调用方看到的是
   "有效期读不出来"，而真正的问题是文件坏了 —— 提示指向了错误的方向。
   修法：解析失败即报错。

3. **`ServeTLS` 起了两个服务。** 它先调 `startLocked`（那会立刻起一个
   **明文 HTTP** 服务并占住监听），随后试图在同一个监听上做 TLS。
   客户端在握手阶段收到的是明文响应，报错是
   `first record does not look like a TLS handshake` ——
   完全看不出根因是"起了两个服务"。
   修法：把"准备"与"服务"拆开，两种模式共用准备动作。

#### TLS 的几处设计

- **用 `GetCertificate` 而不是静态证书列表**：证书是运行期陆续签发的，
  用回调之后新证书签好的那一刻就生效，不需要重启监听 ——
  而重启会切断所有在途连接。
- **没有 SNI 时拒绝握手**，而不是随便给一张证书：给错了会让客户端
  看到"证书域名不匹配"，那个提示会把排查引向"证书配错了"，
  而不是"你该用域名访问"。
- **缓存已解析的证书**：`GetCertificate` 在每次握手时都会被调用，
  每次读盘 + 解析 PEM + 解析 X.509 在高频访问下是明显开销。
- **默认最低 TLS 1.2**，ALPN 同时含 `h2` 与 `http/1.1`（少了 h2
  会让浏览器退回 HTTP/1.1，而多路复用正是反代最需要的）。



### M4-b ACME DNS-01（偏离计划并说明理由）

**计划原本写的是集成 certmagic，实际改为直接用 `golang.org/x/crypto/acme`。**

决定性的理由是**新增依赖为零**：`x/crypto` 已经在依赖图里（作为间接依赖），
而 certmagic 会带来 8 个左右的传递依赖。

更重要的是 certmagic 的价值在这里用不上：

- 存储后端 —— 我们自己有 SQLite 与数据目录；
- HTTP-01 / TLS-ALPN 求解器 —— 我们只要 DNS-01；
- 配置文件格式 —— 我们用的是自己的设置；
- libdns 生态 —— 我们有自研的 `dns.Provider` 接口（见 D15），而 Tier-1
  六家已经实现了完整的记录 CRUD，写一份 libdns 适配器反而是多一层无谓的转换。

代价是续期调度与边界情况由我们自己负责。ACME 协议本身由 `x/crypto/acme`
处理 —— 那部分不该自己写。

#### 为什么用 DNS-01 而不是 HTTP-01

HTTP-01 要求 Let's Encrypt 能从公网访问 80 端口。而本产品的目标场景
（国内家宽）里，80 端口经常被运营商封禁；即使没封，也需要额外开一条
防火墙规则 —— 那意味着**证书能否签发取决于一堆与 HTTPS 无关的条件**。

DNS-01 只需要能改 DNS 记录，而那是本产品已经在做的事。

#### 三处最容易出错的地方

1. **通配域名的挑战记录名要去掉 `*`。** 通配证书的挑战记录是
   `_acme-challenge.example.com`，**不带** `*` 前缀。拼错了会得到一个
   永远查不到的记录名，而症状是"授权一直超时"，看不出是名字拼错了。

2. **记录归属的区域必须按标签边界匹配，并选最长的那个。** 用
   `strings.HasSuffix` 会让 `notexample.com` 被 `example.com` 匹配上，
   于是挑战记录被写到了一个用户根本没有的区域里。选错的症状是
   "记录创建成功了，但 ACME 服务器查不到"。

3. **账户密钥丢了就等于换了账户。** ACME 账户由密钥标识，而**已经签发的
   证书无法再用原账户续期**。更糟的是症状有 90 天的延迟：今天一切正常，
   三个月后证书突然过期，那时已经很难把两件事联系起来。
   因此损坏的密钥文件**报错而不是覆盖**，并说明后果。

#### 尚未接线

客户端与存储已完成并有测试覆盖，但**守护进程还没有引用它们** ——
中间证书与私钥还没有被接进反代的 TLS 配置，也没有接口可以触发签发。
下一步要做的：ACME 设置项、证书管理器（自动续期）、`/v1/certs` 接口、
以及在代理的 `tls.Config.GetCertificate` 里按 SNI 取证书。



### M4-a2 把反代接到内核上

#### 路由用整体替换而不是增删改

规则表必须**始终自洽**：同一个域名不能同时指向两个上游。增量修改会让
"检查冲突"变成一件需要跨多次调用才能完成的事，而中间任何一个时刻的
状态都可能有冲突 —— 那期间进来的请求会打到哪一条是不确定的。

整体替换让"检查 + 生效"变成一次原子操作。

#### 真机上抓到的三个缺陷

1. **代理未运行时无法保存路由。** `SaveRoutes` 在没启动监听时返回
   "代理未在运行" —— 而"先规划好路由、再开启代理"是最自然的顺序，
   用户会以为是自己填错了什么。修法：未运行时只落库、不生效，
   路由在下次启动时加载。

2. **设置里的代理字段被静默忽略。** 我给 `Settings` 结构体与 `Patch`
   都加了字段，却**忘了在 `Service.Update` 里应用它们** —— 于是接口
   返回 200、字段却还是旧值。这类"加了字段但没接线"的疏漏不会产生
   编译错误，只会在用户点开开关时表现为"什么都没发生"。

3. **监听成功把路由加载的错误清掉了。** `Status().Error` 共用一个
   `lastErr`，而监听成功后会把它清成 nil。于是"路由加载失败但监听
   成功"这种情况下状态里什么都不剩，用户在界面上只看到"代理在运行"
   却发现所有请求都是 404。修法：加载错误与监听错误分开记录。

#### 真机验证

```
1. 先配置路由（代理未开启）
   已添加：home.example.com → 127.0.0.1:52784
2. 开启反向代理
   proxy_enabled=True  proxy_port=18080
   运行中：监听端口 18080，1 条规则
3. 经代理访问内核接口（Host: home.example.com）
   HTTP 200  →  {"status":"ok","uptime_seconds":4,...}
4. 未知域名
   HTTP 404  →  没有为此域名配置转发规则
```

第 4 条是刻意的：没有默认上游。回退会让"随便一个域名指向这台机器"
都能打到某个本地服务上，而用户完全不知道自己的服务被谁访问了。



### M4-a 反向代理核心

**它为什么必须存在**：一个家庭网络通常只有**一个**能开放的入口，
而用户想跑的服务往往有好几个。没有反代就只能"每个服务一个端口"硬撑，
而那意味着每加一个服务都要再开一个端口、再配一次证书。

#### 三条安全边界（对应 R10）

反代跑在公网上，因此它天然是攻击面：

1. **不能变成开放代理。** 上游只允许回环与私有网段。若允许任意上游，
   任何人都能拿这台机器当跳板 —— 请求进来、出去打第三方，
   而所有流量都记在用户头上。开放代理是被扫描器**主动寻找**的东西，
   一台暴露几小时的家用机器就会被找到并滥用。
2. **不信客户端给的身份头。** `X-Forwarded-*` / `X-Real-IP` 由客户端
   随意伪造，必须清掉再填正确的值。应用常靠它们判断"请求来自哪里"，
   而让它相信伪造的值会让 IP 白名单之类的机制完全失效。
3. **不转发 CONNECT。** 那等于把开放代理的洞开在 TLS 层。

#### 两个容易被忽略的细节

**校验必须发生在实际连接的那个 IP 上。** 配置时校验过不代表连接时
还合法：主机名会被 DNS 重新解析，而 **DNS rebinding** 正是利用这一点 ——
配置时域名解析到 `127.0.0.1`（通过校验），随后改解析到公网地址
（变成跳板）。因此本包用自定义的 `DialContext`，在每次连接前校验，
并且**用校验过的那个 IP 拨号**，而不是把主机名交给拨号器再解析一次
（后者会让"校验的地址"与"连接的地址"之间存在一个可被利用的窗口）。

**通配只匹配一级，且不匹配裸域名。** `*.example.com` 匹配
`a.example.com`，但**不**匹配 `example.com`，也**不**匹配
`a.b.example.com` —— 这与 TLS 证书的通配规则一致。放宽它的后果是
用户拿到一个证书不匹配的域名，而浏览器只会说"证书无效"，
很难联想到是路由配错了。

#### 测试中抓到的两件事

1. **`httptest.ResponseRecorder` 不支持连接劫持。** 用它测 WebSocket
   会得到一个 502，看起来像"透传坏了"，实际只是测试工具不支持 ——
   101 响应要求代理劫持底层连接。
2. **假上游必须真正完成协议升级。** 直接 `w.WriteHeader(101)` 而不
   劫持连接会让 Go 的 http 服务器异常关闭连接，代理那边看到的是连接
   错误。这两条都不是产品缺陷，但都会让测试给出误导性的结论。

#### 尚未接线

代理目前是一个独立包，**内核还不会启动它**，也没有接口可以配置路由。
下一步要做的：路由持久化、`/v1/proxy/routes` 接口、守护进程启动监听、
`isc proxy` 命令。



- **`certmagic` 集成**：通过 `libdns_adapter` 让 certmagic 使用 Tier-1 provider 做 DNS-01；
- **反向代理**：
  - 基于 `net/http/httputil.ReverseProxy`；
  - 域名路由 + SNI 路由（`tls.Config.GetCertificate`）；
  - 单个非标端口承载多个域名的入口；
  - WebSocket 透传；
- **证书生命周期**：首次申请、到期前自动续期、续期事件推送；
- **请求头与安全**：清理由客户端伪造的 `X-Forwarded-*`，追加正确值；禁止开放代理语义。

**验收**
1. 在只开放一个非标端口的前提下，两个不同域名分别路由到两个本地服务；
2. HTTPS 证书由 Let's Encrypt 通过 DNS-01 自动签发，无需开放 80；
3. 证书到期前自动续期并推送 `cert.renewed` 事件。

## 7. M5 — 打磨与打包

### M5-a 三平台服务安装

三个后端：Windows 服务控制管理器（SCM）、Linux systemd、macOS launchd。
用统一的 `isc service install/uninstall/status/start/stop` 操作。

#### 内容生成与平台调用分开

生成 unit / plist 的内容是**纯字符串逻辑**，而它恰恰是最容易出错的部分：

```
引号     含空格的路径不加引号会被拆成两个参数
转义     plist 是 XML，路径里的 & 会让它无法解析
注入     参数里的换行符会越出那一行配置
```

而"写文件、执行 systemctl/launchctl"才是真正平台相关的部分。因此内容生成
放在**没有构建标签**的 `service_def.go` 里 —— Linux 与 macOS 的服务安装在本机
做不到真机验证（R8），把这些逻辑做成可跨平台测试的，是那两块唯一的质量保证。

#### 这个决定立刻抓到了一个真 bug

`filepath.Dir("/usr/local/bin/isc")` 在 Windows 上返回 `\usr\local\bin` ——
因为 `filepath` 用的是**宿主操作系统**的分隔符。同理
`filepath.IsAbs("/usr/local/bin/isc")` 在 Windows 上是 **false**。

我原本声称这些函数"平台无关"，而**第一次运行测试就证明了这个说法是错的**。

区分开来看：

| 函数 | 校验/生成的对象 | 该用哪个包 |
|---|---|---|
| `RenderSystemdUnit` / `RenderLaunchdPlist` | **目标平台**的配置文件 | `path`（永远是 Unix 路径） |
| `ValidateServiceConfig` | **当前主机**的配置 | `filepath`（Windows 上是 `C:\...`） |

#### `isc service status` 报两件事

真机上确认：**Windows 上查询服务状态同样需要管理员**（打开 SCM 要完全访问权），
普通用户跑这条命令会失败。这推翻了"查询不需要权限"的假设。

但它也暴露了更根本的问题：用户问"服务在跑吗"，真正想知道的是"**内核**在跑吗"，
而那个问题不需要任何权限就能回答。因此状态命令报两行：

```
⏹  内核：未运行
   系统服务：无法查询（windows-scm）
   platform: 查询服务状态需要管理员权限…
```

服务查询失败**不让整条命令失败** —— 上面那行已经回答了用户最可能想问的问题。

#### 各平台的重启策略

后端都刻意用"**只在异常退出时重启**"而不是"总是重启"：

- systemd `Restart=on-failure`
- launchd `KeepAlive` + `SuccessfulExit=false`
- Windows 恢复动作（三次递增延迟）

用"总是重启"会让用户主动 stop 之后服务立刻被拉起来 —— 那是"我明明停掉了它"
这类困惑的来源。

systemd 侧还加了 `StartLimitBurst=5`：没有它的话，一个必然启动失败的配置会让
系统日志被刷满，而用户完全看不出"它在反复重启"。

#### Linux .deb（已实现）

`go run ./scripts/release` 现在额外产出 `isc_<版本>_<架构>.deb`，装法与其它
Debian 包一致：

```
sudo apt install ./isc_0.1.0_amd64.deb     # 或 sudo dpkg -i
isc service install                        # 再注册为系统服务
```

**包刻意不自带 systemd unit**：服务由 `isc service install` 注册，而那让用户
可以自己决定要不要开机自启。包一装上就自启，对"我只是想试试"的人来说是个
不愉快的意外。

##### 为什么手写 ar 而不用 dpkg-deb

构建要在三个平台上都能跑，而 `dpkg-deb` 只在 Debian 系上存在 —— 用它就意味着
"在 Windows 上打不出 Linux 的包"，而交叉编译恰恰是本项目发布方式的常态。

deb 的格式本身很简单（ar 归档 + 两个 tar.gz），而手写它换来的是**产物可以被
逐字节解析验证** —— 这一点比"调用一个本机没有的工具"有价值得多。

##### 外部工具交叉验证

生成的 `.deb` 用 Windows 自带的 `tar`（bsdtar，一个**独立的实现**）读取：

```
$ tar -tf isc_0.1.0_amd64.deb
debian-binary
control.tar.gz
data.tar.gz
```

成员名与顺序完全正确。测试里的 ar 解析器也是独立实现的（不复用生成代码）——
用同一份代码生成再解析等于什么都没验证。

##### 解包核对抓到一个被压缩掩盖的缺陷

逐条核对 `data.tar.gz` 的内容时发现：

```
-rw-r--r--  0 0  18354336  ./usr/share/doc/isc/isc      ← 18MB 的二进制
```

暂存目录里同时有可执行文件与文档，而"把目录里的文件全拷过去"把二进制也塞进
了文档目录 —— **二进制在包里存了两份**。

只看包大小发现不了它：压缩把体积差掩盖了（15.5MB 的包 vs 18.3MB 的二进制）。
修掉之后包从 **15.5 MB 降到 7.41 MB**，超过一半。

##### 顺带修掉两个 flaky 测试

同一轮里有两条通知中心的测试在机器有负载时失败（当时正同时跑着发布构建）。

它们的断言依赖墙上时钟（"384 次提交要在 100ms 内返回"、"等 120ms 后静默期
一定过了"），而**这类断言在负载下测的是机器有多闲，不是代码对不对**。

修法不是放宽到"总能过"，而是让断言测回它本来要测的东西：

- `Notify` 不阻塞：预算从 100ms 放宽到 2 秒 —— 而这不削弱断言，因为如果
  它真的会等通道发完，384 条 × 200ms = 76 秒，与 2 秒差了近四十倍。
- 静默期：从 80ms/120ms 改成 250ms/600ms，留出两倍以上间隔。

改完在**有负载的情况下连跑 3 次全过**（这是验证 flaky 修复的唯一办法）。
#### Linux .rpm（已实现）

```
sudo dnf install ./isc-0.1.0-1.amd64.rpm     # 或 sudo rpm -i
```

RPM 的格式比 deb 复杂得多，而**它同样可以被逐字节解析验证**：

```
Lead            96 字节的遗留头
Signature       一个 header 结构，含校验和与尺寸
Header          一个 header 结构，含元数据与文件清单
Payload         cpio(newc) 归档，gzip 压缩
```

header 结构是二进制索引表（每条 16 字节：tag / type / offset / count），
而 cpio 的头部是 **110 字节的十六进制文本**。两处都容易写出"生成时不报错、
安装时才失败"的问题。

##### 那个"二进制被复制进文档目录"的缺陷又抓了我一次

在 deb 那边，它是解包核对时发现的（包从 15.5MB 降到 7.41MB）。因此写 RPM
时我从一开始就加了排除逻辑 —— 而测试**立刻失败**了：

```
可执行文件被复制进了文档目录 /usr/share/doc/isc/isc —— 包里存了两份
```

成因不同：这次是**用错了包**。`opts.BinaryPath` 是**宿主路径**
（Windows 上是 `C:\...\stage\isc`），而我用了 `path.Base` —— 那个包只认
`/` 作分隔符，于是它返回整个字符串，排除判断永远不成立。

区分很清楚：

| 处理对象 | 该用哪个包 | 为什么 |
|---|---|---|
| **安装路径**（`/usr/bin/isc`） | `path` | 它们永远是 Unix 路径，与构建机无关 |
| **宿主路径**（`opts.BinaryPath`） | `filepath` | 在 Windows 上是 `C:\...` |

这与 M5-a 里 `filepath.Dir("/usr/local/bin/isc")` 那个缺陷是**同一类问题的
两个方向**。同一个项目里出现两次，说明"路径该用哪个包"值得当成一条明确的
规则写下来，而不是靠每次都想一遍。

##### RPM 对版本号的限制

RPM 用连字符分隔 `Version` 与 `Release`，因此 `Version` 里**不能有连字符**。
而我们的版本可能来自 `git describe`（例如 `1.0.0-rc1`）。

处理方式是显式挡住并说明该怎么改，而不是让 rpm 在安装时报一句含糊的
"版本号非法"；构建脚本侧则把连字符换成下划线（保留分隔，比直接删掉更可读）。

##### CI 上用真正的 rpm 验证

Ubuntu runner 上装了 `rpm`，因此 release-build job 里多了一步：
`rpm -qip` / `-qlp` / `-qplv` 逐项核对、检查可执行位、检查二进制没有被
复制进文档目录、以及 `rpm -K` 校验载荷完整性。

这比单元测试更强：单元测试用的是我们自己写的解析器，而这里是 RPM 自己的工具。
关于**为什么压缩包是这类工具的正常形态**：`kubectl`、`terraform`、`caddy`
这些同为"单一 Go 可执行文件"的工具都是这么分发的 —— 因为产物没有依赖，
"安装"这个动作本身没有多少内容可做。而本项目的"安装"是
`isc service install`（注册服务、开机自启、崩溃重启），那一步已经实现。

关于**代码签名**：它不是一个可以"写出来"的功能。没有证书就无法签名，而没有
签名的 Windows 安装包会被 SmartScreen 拦下、macOS 上会被 Gatekeeper 拒绝。
这属于外部依赖，不是代码缺口。

**因此这里留下的是一条待决事项而非未完成的功能**：如果将来要做系统级安装包，
`.deb` 与 `.rpm` 不需要证书、可以纯粹由构建脚本产出（`ar` + `tar` + control
文件），而 `.msi` / `.pkg` 与签名需要证书到位之后才有意义。

### M5-b 构建与打包

`go run ./scripts/release` 一次产出 7 个平台的产物 + `SHA256SUMS`。

#### 为什么用 Go 而不是 shell 脚本

项目要出三个平台的产物，而构建本身也得在那三个平台上都能跑。用 PowerShell
写就得再维护一份 `.sh`，两者迟早会漂移 —— 而漂移的表现是"在某台机器上打出
来的包少了一个平台"。

Go 程序在任何装了 Go 的机器上行为一致，而且它能被 `go vet` 覆盖。

#### 可复现构建不是洁癖

第一次做可复现性检查时，连跑两次的产物**哈希不同**。原因是构建时间通过
ldflags 注入，每次都变。加了 `SOURCE_DATE_EPOCH`（可复现构建的通行约定）
之后 tar.gz 一致了，而 **zip 仍然不同**。

第二次的原因不同：`zip.FileInfoHeader` 会把文件在**磁盘上的修改时间**写进
zip 头，而编译产物每次构建的 mtime 都不同。修法是固定成 `1980-01-01`
（ZIP 格式能表示的最早时间，零值会被编码成未定义值）。

最终 7 个产物与 `SHA256SUMS` 在两次构建之间**逐字节相同**。

这件事为什么重要：这个内核会拿到用户的 DNS 凭据，因此"校验和一致"应当
能证明"两个产物来自同一份源码" —— 而如果构建本身不可复现，那个证明是
不成立的。

#### 打包时的几处考虑

- **产物名带版本号**：用户下载一堆包时，文件名是他唯一能看到的版本信息。
- **许可证必须随包分发**：GPLv3 的要求，而用户拿到一个二进制却找不到许可证
  与来源，是无法接受的分发方式。因此 `LICENSE`、`THIRD_PARTY_NOTICES.md`、
  `README.md` 都打进包里。
- **`-trimpath`**：不去掉的话构建机上用户的目录名会被写进二进制 ——
  那既是隐私问题，也让构建不可复现。
- **CGO_ENABLED=0**：本项目的硬约束。开了 cgo 就需要目标平台的 C 工具链，
  而交叉编译时那通常没有 —— 表现是"某个平台的构建莫名失败"。
- **Windows 用 zip，其余用 tar.gz**：Windows 用户习惯双击解压；tar.gz 在
  Unix 上是标准且能保留可执行位。

### M5-c 文档

`README.md` 面向**用户**而不是开发者，重点在三处：

1. **快速上手**按"先跑起来 → 配凭据 → 建任务 → 确认通了 → 需要时上 HTTPS"

#### 这一轮又抓到一个只在 Windows 上复现的缺陷

加了 `TestPackTarGzSetsExecutableBit` 守住它，并**验证过这个测试确实能抓到
那个 bug**（临时撤掉修复后它失败，报 `isc 的权限是 0666，没有执行位`）。

它不是一次性的验证。这条性质已经抓到过**两次**：ldflags 里的构建时间，

而是靠"跑两遍比一比"。

而它为什么重要：这个内核会拿到用户的 DNS 凭据，因此"校验和一致"应当能证明
"两个产物来自同一份源码" —— 如果构建本身不可复现，那个证明是不成立的。

### A3. 回滚在第一步失败时停下 —— 取舍没有被写下来（次要）

`internal/change/runner.go` 的 `rollbackSteps` 在某个步骤撤销失败时**立刻返回**，
剩余的步骤不再尝试。

它留下的状态是"部分撤销"，而这一点**对用户是可见的**：变更状态会显示
「回滚失败（系统处于中间状态）」，`isc doctor` 也会把它列出来。所以行为本身
是诚实的。

缺的只是一句注释说明**为什么选择停下而不是继续**。两种做法各有道理：

- **停下**（现状）：避免在一个已经不确定的系统上继续动手，防止把状态改得更乱；
- **继续**：尽可能回到执行前的样子，哪怕过程中有一步失败。

现状选择了前者，且把结果如实报给了用户 —— 因此这不是缺陷，而是**没有被写下
取舍理由**。它值得记下来是因为：后来的人看到"第一个失败就返回"时，无法判断
那是有意为之还是写漏了 `continue`。
