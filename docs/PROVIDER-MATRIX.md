### 为什么多数服务商没有「凭据校验」

「测试连接」需要一个**只读**的校验端点。阿里云 / 腾讯云 / 华为云 /
GoDaddy 都没有 —— 用"列一次域名"来冒充会要求额外的权限，把只有
DNS 编辑权限的**最小权限账号误判为无效**，那是比没有更糟的结果。

Cloudflare 有专门的 `GET /user/tokens/verify`，因此它能校验。
DNSPod 其实也有（`Info.Version`），当前未接 —— 接的话记得能力位会跟着变，
`TestTier1ProvidersAreVerifiableOrHonest` 会守住这一点。

## 各家的记录模型差异

### 记录的「身份」是什么

这是各家差异最大、也最容易出事的地方。

| 服务商 | 记录定位方式 | 删除的真实粒度 |
|---|---|---|
| Cloudflare | 独立记录 ID | 一条 |
| 阿里云 | `RecordId` | 一条 |
| 腾讯云 | `RecordId`（数字） | 一条 |
| DNSPod | `record_id` | 一条 |
| 华为云 | recordset ID | **整个记录集** |
| GoDaddy | 合成的 `type\|name\|data` | **整个 (type, name) 组合** |

#### 华为云：recordset 而非单条记录

华为云的模型是**记录集**：同一个名字+类型的多条值放在一个 recordset 的
`records` 数组里。ISC 的 `dns.Record` 是"一条记录"，因此：

- **读**：一个 recordset 展开成 N 条 `dns.Record`，**共享同一个 ID**。
  调用方不能拿 ID 当唯一键。
- **写**：提交的记录被翻译成"这个记录集的值就这一个"。
  **改一条 = 整个记录集被改成一个值；删一条 = 删掉整个记录集。**
- 多值记录集里改/删"一条"会**波及其余的值**。界面必须在确认文案里
  明确告知，否则用户会在毫无察觉的情况下丢数据。
- 反向也做不到：**无法"给同名同类型再加一个值"**，Create 会被服务商拒绝。

#### GoDaddy：记录根本没有 ID

GoDaddy 用 `(type, name)` 定位记录，同名同类型可以有多条值。因此：

- 读出时**合成** ID：`type|apiname|data`，三段各自百分号编码
  （TXT 里可以合法出现 `|`，直接拼接会让解析边界错乱）。
- **合成 ID 不稳定**：`data` 变了 ID 就变了。**拿隔夜的 ID 更新会失败。**
- 解析不出来时**报错而不猜** —— 猜错等于静默改错记录。
- 更新前会校验 ID 与提交记录的 `(type, name)` 一致，**不一致直接报错
  且一个请求都不发**。
- `DeleteRecord` 删掉**整个 (type, name) 组合的全部记录**，没有单条粒度。
  先读后写也绕不开（`PUT` 表达不了"少一条"）。

> **界面义务**：调用方在删除确认文案里**必须**说明这会删掉同名的其它值。
> 后端已经如实实现了语义，但用户看不到这一层。

### 记录内容的字段映射

| 概念 | Cloudflare | 阿里云 | 腾讯云 | DNSPod | 华为云 | GoDaddy |
|---|---|---|---|---|---|---|
| 内容字段名 | `content` | `Value` | `Value` | `value` | `records[]` | `data` |
| 根记录写法 | `example.com` | `@` | `@` | `@` | 区域名 + 结尾点 | `@` |
| 优先级 | `priority` | `Priority` | `MX` | `mx` | 编在值字符串里 ⚠ | `priority` |
| 备注 | `comment` | `Remark`（只读）| `Remark` | `remark`（只读）| `description` | — |
| TTL = 0 的含义 | 发 `1`（auto） | 发 `600` | 不发送该字段 | 不发送该字段 | 新增发 `300`，修改不发送 | 发 `3600` |
| 区域名结尾的点 | 无 | 无 | 无 | 无 | **有**（收发都带） | 无 |

## 已知限制与未验证项

按「影响面 × 确定性」排列。**未验证**指的是没有真实账号联调过。

### 会影响数据正确性

| # | 服务商 | 问题 | 现状 |
|---|---|---|---|
| 1 | 华为云 | 改/删多值记录集会波及其余值 | 已如实实现并在注释说明；**界面必须提示** |
| 2 | GoDaddy | 删除是整个 `(type,name)` 组合 | 同上 |
| 3 | GoDaddy | 合成 ID 在 `data` 变化后失效 | 已实现校验；隔夜 ID 会报错而非静默改错 |
| 4 | 阿里云 | `UpdateDomainRecord` 省略 `Line` 的语义未确认（文档只说"默认为 default"） | 按"会被改回默认"防御：先读回原线路再原样送回；**读不回则让修改失败** |
| 5 | 阿里云 | 需要 `DescribeDomainRecordInfo` 权限，否则改记录会失败 | 副作用已知；错误信息是服务端原话 |
| 6 | 腾讯云 | 同上（`UpdateRecord` 先读一次原线路） | 读失败时**回退到默认线路**（与阿里云策略不同：那边是不让改，这边是尽力而为）|
| 7 | DNSPod | 同上（`Record.Modify` 的 `record_line` 必填） | 读失败即停，不退化成"不读直接改" |
| 8 | DNSPod | **企业 VIP 的 `weight`（权重）在每次修改时会丢失** | `Record.Info` 未解析该字段；未证实不传是否安全 |
| 9 | 华为云 | MX/SRV 优先级编在值字符串里（推断） | 值原样往返，即使推断错也不会改坏数据；但 `Priority` 恒为 0 |
| 10 | 阿里云 / 华为云 | SRV 的优先级表达未验证 | 同上 |
| 11 | GoDaddy | SRV 的 `port`/`weight`/`protocol`/`service` **不发送** | `dns.Record` 没有对应字段；改 SRV 会丢这四个参数 —— **部分支持** |

| 16 | 腾讯云 | `CreateRecord`/`ModifyRecord` 只回 `RecordId`，不回显整条记录 | 返回"入参 + 服务端给的编号"，而不是假装解析出最终状态 |

### 有意为之的取舍

| # | 范围 | 取舍 | 理由 |
|---|---|---|---|
| 20 | 阿里云 / 腾讯云 / DNSPod | 区域列表**过滤掉非活跃域名** | 在 pending / pause / spam 状态下改记录不会生效，列出来只会让用户以为"改了没用"。代价：看不到自己暂停的域名 |
| 21 | 华为云 | 区域列表**不过滤状态**（与上面相反） | 华为云有十来个状态值，猜错一个词会把用户域名从列表里藏掉，而用户无法自救；多列出最多是被服务商拒绝并回一句原因 |
| 22 | 阿里云 / 腾讯云 / DNSPod / 华为云 | 过滤时下发关键字后**仍在客户端精确复核** | 上游是模糊匹配（`RRKeyWord` 会把 `wwww` 也带回来） |
| 23 | 华为云 | 翻页**不用**"不满一页即最后一页"作为终止条件 | 服务商截断 `limit` 时会静默漏数据；代价只是 `total_count` 缺失时多一次请求 |
| 24 | DNSPod | TTL 按官方文档的**区间**（1–604800 + 套餐最小值）实现，**不按离散档位取整** | 官方文档给的是区间而非档位表；取整等于静默改数据（900→1800） |
| 25 | DNSPod | `status.code` 同时接受字符串 `"1"` 与数字 `1` | 同一套 API 在不同接口间确实混用类型；只认一种的代价是整家服务商解析失败（有 8 种组合的测试） |
| 26 | 华为云 / 阿里云 | 写操作**不使用** `search_mode=equal` 之类的精确模式 | 精确模式是否要求结尾的点、是否区分大小写都无实证，猜错会**静默返回空列表** |
| 27 | 全体 | 记录内容不做本地格式校验 | 各类记录的规则差异极大（TXT 有空格、CAA 有结构、SRV 有下划线前缀），本地猜测只会误伤合法输入。交给服务商，把它的原话转达用户 |

## 验证方式

每家的实现都由**假服务器测试**覆盖，断言的是**契约**而非实现细节：

- 发出的请求长什么样（URL、方法、字段名、头）
- 响应被翻译成了什么（字段映射、TTL 归一、优先级、根记录）
- 错误分支（401 / 404 / 429 / 业务错误 / 畸形响应）
- **凭据不出现在任何请求或错误信息里**

部分实现额外做了交叉校验：
- 阿里云：用 `ddnsgo.HmacSignToB64` 对**实际发出的查询串**重算签名并比对
- 华为云：用假服务器**实际收到的内容**重算签名并比对（路径/查询串/请求体/头集合任一不一致就露馅）
- 腾讯云：断言 TC3 签名作用域里是 `/dnspod/tc3_request`

**没有做真实账号联调。** 上面「未验证」一栏列出的都是由此而来的缺口。
